1. What changes when the arithmetic leaves the CPU?

In Chapter 28, you made CPU tensor operations faster while preserving a scalar reference. A GPU offers many more arithmetic lanes, but calling it requires a different agreement. Rust prepares resources and commands on the host. A shader describes work for thousands of numbered invocations. The queue accepts that work asynchronously. The answer remains in GPU memory until we explicitly copy and map it.

Our visible goal is deliberately small: add two five-element vectors on a hardware Vulkan adapter and recover [3, 3, 3, 9, 1]. An invocation is one execution of the shader entry function, with its own ID. Small arithmetic leaves nowhere for plumbing bugs to hide. If the output is wrong, we can inspect the five inputs, five invocation IDs, one addition, and the readback path. Once that path is trustworthy, later chapters can replace addition with reductions, matrix multiplication, and training.

“A GPU result” must identify a GPU.

A software Vulkan implementation can execute the same shader on CPU cores. That is useful in some environments, but it does not verify hardware execution. The project enumerates Vulkan adapters, reports their names, device types, drivers, and backends, rejects CPU adapters, and prefers discrete hardware. If no hardware Vulkan adapter exists, it returns an unsupported error instead of silently changing the experiment.

The complete route is:

Rust slices → GPU storage buffers → bind group → compute dispatch → output storage → staging copy → mapped Rust values

Every arrow is an operation. A compute shader does only the middle arithmetic. Adapter selection, memory usage flags, dispatch size, synchronization, and validation remain host responsibilities.

Code and terminology carried forward

Chapter 25 introduced f32 performance kernels and absolute-plus-relative comparisons. Chapter 28 compared an optimized CPU operation with a scalar oracle and handled a final partial SIMD vector. This chapter keeps those conventions and moves a simpler elementwise operation across a device boundary. Both left and right are contiguous one-dimensional slices with shape [N]; output has the same shape and order. See the course-wide code and numerical conventions.

The CPU and GPU functions keep prediction-side names out of this chapter because they implement a device primitive, not a model, loss, gradient, or training step. The aligned dispatch_params uniform is dispatch metadata; it contains no learned parameters. Here “GPU compute kernel” means the actual WGSL entry point add. It is distinct from the statistical kernel K(a, b) owned by Chapter 16, which measures similarity for a classifier.

fn dispatch_count(element_count: usize, workgroup_size: usize) -> usize {
    element_count.div_ceil(workgroup_size)
}

The starter and both CPU exercise files use this same function name, argument order, and units. The reference uses its result as the x dimension passed to dispatch_workgroups.

2. Discover the device before requesting it

wgpu presents a portable API over backends such as Vulkan, Direct3D, Metal, and browser WebGPU. This course's checked hardware route is Vulkan, so the instance enables only Backends::VULKAN. It then asynchronously enumerates every Vulkan adapter. An adapter describes a candidate; it is not yet the logical device used to create buffers.

let mut descriptor = wgpu::InstanceDescriptor::new_without_display_handle();
descriptor.backends = wgpu::Backends::VULKAN;
let instance = wgpu::Instance::new(descriptor);
let adapters = pollster::block_on(
    instance.enumerate_adapters(wgpu::Backends::VULKAN)
);

Enumeration is preferable to relying only on a high-performance preference. A preference is allowed to be soft. Explicit inspection lets the program reject DeviceType::Cpu and choose a discrete GPU when one is present. It still accepts non-CPU integrated or virtual hardware if that is the only hardware Vulkan choice. The selected adapter's name and backend are printed before device creation, so a saved run contains basic provenance.

The adapter creates a logical Device and Queue. The device creates validated resources and pipelines. The queue receives finished command buffers. wgpu 29 is pinned because GPU APIs evolve quickly; the course code was compiled against that exact local source. pollster only bridges the few asynchronous setup calls into this small synchronous command-line program. bytemuck converts plain f32 and u32 slices to bytes without hand-written unsafe code. Neither dependency supplies ML operations.

Selection on the course host

The target is an AMD Radeon RX 6950 XT exposed by RADV NAVI21 through Vulkan. The program does not hard-code that name. It asks the runtime and prints what it finds. Hard-coding would reject legitimate learner hardware and could still lie if the named device were absent. Filtering by backend and device type expresses the actual requirement.

3. Give bytes a shape and a purpose

The two Rust inputs are contiguous f32 slices. Each value occupies four bytes. For a length N, one vector therefore needs 4N bytes. Our five-element vectors each need 20 bytes. The shader views these bytes as runtime arrays of f32:

@group(0) @binding(0) var<storage, read> left: array<f32>;
@group(0) @binding(1) var<storage, read> right: array<f32>;
@group(0) @binding(2) var<storage, read_write> output: array<f32>;

The storage buffer usage is a contract. Inputs need STORAGE. The output needs STORAGE | COPY_SRC because the shader writes it and the encoder later copies it. The staging buffer needs COPY_DST | MAP_READ. Mapping the storage output directly would violate the intended usage combination on portable WebGPU.

A fourth uniform buffer carries dispatch_params as four u32 values in this exact order: [element_count, padding, padding, padding]. element_count is N measured in f32 elements, not bytes. WGSL uniform structures obey alignment rules, so the 16-byte host record matches DispatchParams, whose first field has the same name and unit. The bind group connects each numbered shader binding to its concrete buffer. A pipeline describes the shader entry point named add.

One invocation, one answer

For invocation i = 2, the shader reads left[2] = 3.5 and right[2] = −0.5. It stores output[2] = 3.0. Invocation i = 4 stores 0.25 + 0.75 = 1.0. No invocation needs another invocation's value, so there is no shared memory or barrier yet.

Rust validates equal, nonzero lengths and finite input before discovering a GPU. These are caller errors, not device failures. It also converts the slice length to u32 and computes byte size with checked arithmetic. A GPU should not turn malformed dimensions into a validation panic or an accidental allocation.

4. Launch extra lanes safely, then synchronize

The shader declares @workgroup_size(64). One workgroup contains 64 local invocations. The host needs ceiling division:

groups = ⌈N / 64⌉ = (N + 63) / 64

In Rust 1.96, dispatch_count uses element_count.div_ceil(workgroup_size). N = 5 launches one group, which creates IDs 0 through 63. N = 67 launches two groups, which creates IDs 0 through 127. Extra IDs are normal. Every invocation checks i < dispatch_params.element_count before any indexed load or store. Without that guard, the partial final group could access memory outside the logical vector.

@compute @workgroup_size(64)
fn add(@builtin(global_invocation_id) id: vec3<u32>) {
    let i = id.x;
    if (i < dispatch_params.element_count) {
        output[i] = left[i] + right[i];
    }
}

Rust records one compute pass, binds the pipeline and group, dispatches the workgroups, ends the pass, and records a copy from output to staging. queue.submit hands the command buffer to the implementation; submission does not produce a ready Rust vector. Readback begins by requesting an asynchronous map on the staging slice.

The mapping callback sends its result through a standard-library channel. device.poll(PollType::wait_indefinitely()) drives native progress and waits. Only after the callback succeeds does the program borrow the mapped bytes, interpret them as f32, copy them into an owned vector, drop the mapping view, and unmap the buffer. This synchronization is real: removing it would race CPU access against device execution.

Simulation and hardware execution answer different questions.

The scalar oracle proves the expected arithmetic. Successful WGSL parsing proves shader syntax. An ignored test run on a named hardware adapter verifies dispatch and readback. Keep all three claims distinct.

5. Run and inspect the complete path

From the course root, compile and run the small release demonstration:

cargo run --release --manifest-path projects/ch29/Cargo.toml
cargo test --manifest-path projects/ch29/Cargo.toml
cargo test --release --manifest-path projects/ch29/Cargo.toml -- --ignored --nocapture

The ordinary test run checks malformed shapes without requiring a GPU. The last command opts into the hardware test and prints adapter discovery. On a machine without a hardware Vulkan adapter, that command must fail with a clear unsupported message. That failure is evidence about the environment; changing it into a passing CPU fallback would erase the evidence.

Illustrative successful output is:

selected hardware adapter: AMD Radeon RX 6950 XT (Vulkan)
GPU result: [3.0, 3.0, 3.0, 9.0, 1.0]
CPU scalar oracle: [3.0, 3.0, 3.0, 9.0, 1.0]

The 67-element ignored test matters more than the pretty five-element printout. Sixty-seven is three more than a full 64-lane group, so it detects floor division and missing bounds checks. Each f32 result must satisfy |actual − expected| ≤ 10⁻⁶ + 10⁻⁶|expected|. Addition should normally match exactly, but this absolute-plus-relative rule states what “matches” means and carries forward to kernels that can fuse operations or reorder reductions. The default executable also rejects a result outside that tolerance.

Debugging · The fifth value remains zero

A program uses element_count / workgroup_size for a four-lane shader and N = 5. Buffers and bindings are correct. Explain the zero before editing.

Answer

Floor division dispatches one workgroup, so IDs 0–3 run and element 4 never gets an invocation. Use dispatch_count(element_count, workgroup_size) and keep the shader's upper-bound guard because the second workgroup also creates IDs 5–7.

Independent variation · SAXPY

Extend the shader to compute output[i] = scale * left[i] + right[i]. Put scale after element_count in the existing aligned uniform, mirror that field order on the Rust host, use scale = 0.5, and predict the five outputs before running. Update the scalar oracle to the same formula before comparing.

Worked answer

For the bundled vectors the result is [2.5, 4, 1.25, 5, 0.875]. The buffer route, [N] shape, argument order, and dispatch count stay unchanged; the host and shader both add the scale field, and both arithmetic paths change to the same formula.
