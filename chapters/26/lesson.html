Chapter 25 gave us a benchmark that can tell the truth. Now we change the work it measures. Matrix multiplication performs the same products under several legal loop orders, but those orders visit memory very differently. This chapter begins with the scalar formula, measures two loop organizations, adds cache blocking, and keeps every output allocation outside the timed kernel.

Milestone

You will multiply nonsquare row-major matrices with scalar row-col-inner, scalar row-inner-col, and blocked row-inner-col kernels. Every version handles odd edge sizes, writes into a reused buffer, and agrees with an f64 reference before any timing is trusted.

Code and terminology carried forward

Chapter 25 measured dense inference with inputs shaped [batch,in_features], weights shaped [out_features,in_features], and caller-owned outputs shaped [batch,out_features]. That layout and the operation Y=inputs×weightsT+bias came from Chapter 9. This chapter keeps the f32 timed kernel, the untimed f64 oracle, the release benchmark protocol, and output-buffer reuse. See the course code and terminology conventions.

General matrix multiplication, or GEMM, writes A[m,k]×B[k,n]=C[m,n]. To express Chapter 25's dense operation as this GEMM, set m=batch, k=in_features, n=out_features, and A=inputs. Chapter 25 stores a dense weight at weights[col*k+inner] because weights are [out_features,in_features]. GEMM needs the explicit transpose B=weightsT, stored contiguously as b[inner*n+col] = weights[col*k+inner]. GEMM then writes C=outputs; dense inference adds bias[col] separately. The benchmark here measures GEMM itself, so it does not time that one-time layout conversion or bias addition.

The code names the three logical indices row, col, and inner before showing any loop. row selects one of the m C rows, col selects one of its n columns, and inner reduces the shared dimension of length k. Textbooks often call the same orders i-j-k and i-k-j; the Rust names spell out the roles because k already stores a dimension length.

1. One product, several traversals

Let A have shape [m,k], B shape [k,n], and C shape [m,n]. Matrix multiplication defines each output by reducing the shared k dimension:

Crow,col = Σinner=0…k−1 Arow,innerBinner,col

In contiguous row-major storage, A[row,inner] is a[row*k+inner], B[inner,col] is b[inner*n+col], and C[row,col] is c[row*n+col]. Chapter 9 owns the glossary definition; here the layout is applied to GEMM. The dimensions are intentionally nonsquare so a hidden transpose cannot pass by coincidence.

Multiply [2,3] by [3,2]

Let A=[[1,2,3],[4,5,6]] and B=[[1,2],[3,4],[5,6]]. C₀₀=1×1+2×3+3×5=22. C₀₁=1×2+2×4+3×6=28. The second row gives C₁₀=4×1+5×3+6×5=49 and C₁₁=4×2+5×4+6×6=64. The flat answer is [22,28,49,64]. Every optimized kernel must reproduce this mapping.

The scalar row-col-inner loop computes one C element at a time. Its inner loop walks one contiguous row of A, but b[inner*n+col] jumps by n values as inner changes. A cache line fetched for one B value contains neighboring columns that this inner loop does not immediately use.

fn matmul_scalar_row_col_inner(
    a: &[f32],
    b: &[f32],
    c: &mut [f32],
    m: usize,
    k: usize,
    n: usize,
) -> Result<(), String> {
    validate_matmul_shapes(a, b, c, m, k, n)?;
    c.fill(0.0);
    for row in 0..m {
        for col in 0..n {
            let mut sum = 0.0;
            for inner in 0..k {
                sum += a[row * k + inner] * b[inner * n + col];
            }
            c[row * n + col] = sum;
        }
    }
    Ok(())
}

The formula fixes which products must contribute to each C element. It does not require one particular traversal. We can reorder independent loops as long as we initialize C once and preserve every contribution.

2. Put contiguous rows in the inner loop

The scalar row-inner-col organization loads A[row,inner] once, then walks col across a complete B row and the matching C row:

fn matmul_scalar_row_inner_col(
    a: &[f32],
    b: &[f32],
    c: &mut [f32],
    m: usize,
    k: usize,
    n: usize,
) -> Result<(), String> {
    validate_matmul_shapes(a, b, c, m, k, n)?;
    c.fill(0.0);
    for row in 0..m {
        for inner in 0..k {
            let a_value = a[row * k + inner];
            for col in 0..n {
                c[row * n + col] += a_value * b[inner * n + col];
            }
        }
    }
    Ok(())
}

Cache locality describes access that reuses nearby or recently used data. The inner col loop has spatial locality: successive B and C offsets are adjacent. A cache line brings several useful f32 values. The A scalar stays in a local variable while it contributes across the row.

These source loops retain the same increasing inner order for each output. Compiler vectorization and fused operations can still affect rounding, so the chapter compares both to an f64 accumulator with tolerance rather than asserting bit equality.

“Contiguous is faster” is a hypothesis until measured. Tiny matrices can fit in cache, and loop overhead or compiler choices may dominate. Some shapes favor transposition or packing, which this chapter does not implement. Run the Chapter 25 protocol in release mode and report observed values for your machine:

3. Reuse a working set before it leaves cache

Loop ordering improves the direction of access, but a large B row and C row may still exceed a nearby cache. Cache blocking, also called tiling, divides matrix axes into smaller ranges. The reference steps row_start, inner_start, and col_start by a block size, then runs the same row-inner-col work inside each tile.

For block=2 and dimensions m=3, k=5, n=4, the first tile covers rows 0..2, inner indices 0..2, and columns 0..2. The next column tile keeps the row and inner ranges but moves to columns 2..4. When inner_start reaches 4, only one shared-dimension value remains. Each upper bound uses start.saturating_add(block).min(dimension), so edge tiles are smaller, even an enormous requested block cannot overflow, and no padding or out-of-bounds read is needed.

fn matmul_blocked_row_inner_col(
    a: &[f32],
    b: &[f32],
    c: &mut [f32],
    m: usize,
    k: usize,
    n: usize,
    block: usize,
) -> Result<(), String> {
    // ponytail: one scalar tile level; add packing/register kernels only after measurements justify them.
    validate_matmul_shapes(a, b, c, m, k, n)?;
    if block == 0 {
        return Err("block size must be positive".into());
    }
    c.fill(0.0);
    for row_start in (0..m).step_by(block) {
        for inner_start in (0..k).step_by(block) {
            for col_start in (0..n).step_by(block) {
                for row in row_start..row_start.saturating_add(block).min(m) {
                    for inner in inner_start..inner_start.saturating_add(block).min(k) {
                        let a_value = a[row * k + inner];
                        for col in col_start..col_start.saturating_add(block).min(n) {
                            c[row * n + col] += a_value * b[inner * n + col];
                        }
                    }
                }
            }
        }
    }
    Ok(())
}

A tile aims to keep useful pieces of A, B, and C near the core while accumulating several operations. Its size is a calibration knob, not a mathematical constant. The reference uses 32 as one reasonable experiment. Real high-performance GEMM uses multiple levels of blocking, packed panels, register microkernels, architecture-specific instructions, and careful scheduling. Adding all of that would hide the central lesson; first prove whether this single tile level helps your actual shape.

Why edge arithmetic stays exact

For n=7 and block=4, col_start takes values 0 and 4. The first inner column range is 0..4, four columns. The second is 4..min(8,7)=4..7, three columns. Together they cover each column exactly once. The same reasoning applies independently to m and k, so an odd 3×5 times 5×7 test exercises partial tiles on all three axes. The test also uses usize::MAX as a block to prove saturating bounds safely reduce it to each dimension.

Blocking can lose. A tile that is too small adds loop overhead; one too large behaves like the unblocked kernel. Cache topology, simultaneous threads, matrix shapes, and other live data affect the best size. Keep the benchmark and tune from evidence rather than naming one universal block.

4. Reuse storage so the kernel comparison stays clean

Each kernel accepts &mut [f32] for C. The caller allocates that vector once and passes the same allocation to every timed repetition. Before multiplication, the kernel calls fill(0.0) because both row-inner-col forms add contributions into existing values. Forgetting the reset silently mixes the current result with the previous repetition.

Allocation reuse separates memory ownership from repeated computation. Training repeatedly creates activations and gradients of known shapes; inference repeatedly writes outputs for similar batches. Holding a correctly sized buffer avoids allocator work and makes latency more predictable. It does not mean stale values may survive. Overwrite every output or clear accumulators at a deliberate boundary.

The timer includes c.fill(0.0) because zero initialization is required by these accumulating kernels. It excludes allocating C because all variants can reuse it. If an application genuinely allocates on every request, measure that end-to-end path separately. Fair comparison requires identical boundaries.

The project’s shape guard checks positive dimensions, checked products, and exact slice lengths before indexing. Block size zero is rejected before step_by. These checks are outside the inner arithmetic and protect the public boundary without putting a branch on every multiply.

Debugging: blocked answers are too small

A learner calls c.fill(0.0) inside the inner_start loop. Why does only the last part of each dot product remain?

Answer

The shared k dimension is split across inner tiles. Each tile contributes a partial sum to the same C entries. Clearing inside the tile loop erases earlier partial sums. Initialize C once before any tile loop, then accumulate through every inner range.

Independent variation: calibrate the block

For the large flag, try block sizes 8, 16, 32, 64, and 128. Run each under identical conditions and write down median and range.

Worked answer

There is no predetermined winner. Choose the fastest stable median for that machine and shape only if the ranges support the difference. If two overlap heavily, report that the experiment cannot distinguish them. A production kernel may need shape-specific or architecture-specific selection, but one measured constant is enough for this course project.

6. Review and transfer

Retrieve: Which index is the reduction axis? Why does row-col-inner stride through B? What does row-inner-col reuse? How do partial tiles avoid out-of-bounds access? Why is clearing C inside an inner tile wrong? Which allocation is excluded from the kernel timer?

Answers

inner reduces the shared k dimension. Holding col fixed while inner changes jumps by n through B. The reordered loop reuses one A scalar while walking adjacent B and C values. Each tile ends at the minimum of its nominal end and the dimension. Inner tiles are partial sums, so only one clear may precede them. C is allocated once by the caller and reused across repetitions.

These kernels remain scalar and single-threaded. They establish correct traversal, edges, and measurement before adding concurrency. In Chapter 27, independent batch rows become thread shards for both inference and gradient calculation.

The benchmark prints m, k, n, precision, architecture, operating system, one execution thread, warmup count, and sample count. Timing includes the same shape checks and output clearing for each kernel.
