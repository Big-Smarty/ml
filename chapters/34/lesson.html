Bytes give complete coverage, but common words consume many prediction steps. Byte-pair encoding learns a compact vocabulary from the training corpus while preserving an exact route back to the original bytes.

Goal

Train, serialize, reload, encode, and decode a deterministic byte BPE tokenizer. The multilingual tests require exact byte round trips, including text whose characters occupy several UTF-8 bytes.

Code and terminology carried forward

Chapter 33 treated each byte as a token ID from 0 through 255. Its Model::logits(input), probabilities(input), predict(input), loss(data), and step(data, learning_rate) keep their model meanings from the course code and terminology guide. This chapter has no predictive model, loss, gradient, optimizer step, or learning rate. It consumes one document's UTF-8 bytes and produces a fitted tokenizer: 256 base-byte entries plus an ordered list of estimated merge rules.

Bpe::fit(data, max_merge_count) is preprocessing estimation, commonly called tokenizer training. It counts adjacent token-ID pairs and may learn fewer than max_merge_count rules when no pair occurs at least twice. It does not perform gradient updates. The Chapter 33 boundary rule still applies: this API accepts one document. A multi-document extension must keep one token-ID sequence per document, aggregate pair counts from windows inside each sequence, and apply each chosen rule inside each sequence; it must not concatenate unrelated endings and beginnings.

1. Text arrives as UTF-8 bytes

Unicode assigns code points; UTF-8 encodes Unicode scalar values as sequences of one to four bytes. ASCII characters retain their one-byte values. The letter é, U+00E9, is encoded as C3 A9. The character 咖, U+5496, is encoded as E5 92 96. Rust strings guarantee valid UTF-8, while Vec<u8> can hold any byte sequence.

A tokenizer maps external text to integer token IDs consumed by a model. It also needs a decoder that maps IDs back to bytes. Starting the vocabulary with all 256 individual bytes guarantees that any input byte sequence is encodable. Learned tokens merely compress frequent adjacent sequences; they never remove the byte fallback.

Count units precisely

The string café has four Unicode scalar values and five UTF-8 bytes: 63 61 66 C3 A9 in hexadecimal. A byte tokenizer initially emits five IDs. If training learns the pair 63+61 as token 256 and then 256+66 as token 257, encoding can emit [257,C3,A9], three tokens. It must still decode 257 to bytes 63 61 66 before appending C3 A9.

Token boundaries need not align with Unicode character boundaries. One token could contain C3 and the next A9. Decoding each token separately as a Rust string would fail, even though concatenating the bytes first produces valid é. Therefore the core decoder returns bytes. Converting the complete result with String::from_utf8 is a separate validation step.

Invalid UTF-8 is data, not permission to guess.

If a caller promises text, reject invalid UTF-8 at that boundary. If the tokenizer API promises arbitrary bytes, preserve them exactly. Replacing invalid bytes with U+FFFD changes data and breaks round-trip identity.

2. Learn merges from adjacent pairs

Byte-pair encoding fitting begins with one token ID per byte. Count every adjacent token-ID pair in data, select the most frequent pair, create a new token ID for its concatenated bytes, and replace non-overlapping occurrences. Repeat until reaching max_merge_count or until no pair occurs twice. This count-and-replace estimation is often called BPE training, but it is distinct from Chapter 33's gradient-based model training.

Fit on banana

Initial IDs spell b a n a n a. Adjacent pairs are ba once, an twice, na twice, and an/na overlap in the middle. Suppose deterministic tie-breaking chooses a n. Assign it ID 256 and replace non-overlapping occurrences, obtaining b 256 256 a. Now pair 256 256 occurs once and 256 a once; no pair occurs twice, so this tiny fitter stops. Decoding ID 256 emits bytes for an.

Overlaps matter. In aaaa, pair a a appears at offsets 0, 1, and 2, but one replacement pass can take offsets 0 and 2 only. A left-to-right scan emits the new token and advances by two on a match. Advancing by one would reuse a byte twice and make decoding invent content.

Frequency ties need a stable rule. The reference chooses the lexicographically smaller pair of existing IDs. This is not the only valid policy, but recording it makes vocabulary training reproducible. A serialized vocabulary without merge order is insufficient: encoding depends on rank. Two tokenizers containing the same byte strings in a different merge order can segment input differently.

Our simple fitter treats the entire supplied byte slice as one document sequence. Concatenating documents would count and possibly learn an artificial pair across the join, just as Chapter 33 would create an artificial next-token target there. A corpus extension needs separate token-ID sequences while counting and replacing. Production tokenizers often pre-segment text and constrain which categories may merge. Such choices affect spaces, punctuation, multilingual compression, and compatibility. They belong in the tokenizer specification and checkpoint, not in an undocumented preprocessing step.

fn fit(data: &[u8], max_merge_count: usize) -> Result<Self, String> {
    if max_merge_count > MAX_MERGES {
        return Err("merge count exceeds u16 vocabulary capacity".to_owned());
    }
    let mut vocab = (0..=255).map(|b| vec![b as u8]).collect::<Vec<_>>();
    let mut token_ids = data.iter().map(|&b| b as u16).collect::<Vec<_>>();
    let mut merge_rules = Vec::new();
    for _ in 0..max_merge_count {
        let mut counts = HashMap::<(u16, u16), usize>::new();
        for pair in token_ids.windows(2) {
            *counts.entry((pair[0], pair[1])).or_default() += 1;
        }
        let Some((&pair, &count)) = counts
            .iter()
            .max_by(|a, b| a.1.cmp(b.1).then_with(|| b.0.cmp(a.0)))
        else {
            break;
        };
        if count < 2 {
            break;
        }
        let id = vocab.len() as u16;
        let mut bytes = vocab[pair.0 as usize].clone();
        bytes.extend_from_slice(&vocab[pair.1 as usize]);
        vocab.push(bytes);
        merge_rules.push(pair);
        token_ids = merge_pair(&token_ids, pair, id);
    }
    Ok(Self { vocab, merge_rules })
}

3. Apply the learned ranks

Encoding starts from byte IDs and applies learned merge rules in training order. For rule r=(a,b) with new ID 256+r, replace all non-overlapping adjacent occurrences. After every rule, the token sequence still decodes to exactly the original bytes. This invariant is stronger than “the output looks right.”

A faster implementation can use heaps, linked positions, or trie-based matching. The chapter uses repeated linear scans because the tiny corpus and vocabulary make the invariant visible. Its cost is roughly O(MN), for M merge rules and N current tokens. That ceiling is deliberate: replace it when profiling a large tokenizer, while retaining the exact slow implementation as an oracle.

Encode with ranked merges

Let rule 0 merge r+u→256, and rule 1 merge 256+s→257. Bytes for rust begin [r,u,s,t]. Rule 0 gives [256,s,t]. Rule 1 gives [257,t]. If the rules were reversed, the second pattern could not exist when checked, so output would remain [256,s,t]. Rank is part of the model.

Decoding is simpler: look up each ID's stored byte string and append it. Reject an ID outside the vocabulary. For a valid tokenizer, every learned entry is the concatenation of two earlier entries, so construction is acyclic. The loader verifies both referenced IDs already exist before accepting a merge.

fn encode(&self, bytes: &[u8]) -> Vec<u16> {
    let mut token_ids = bytes.iter().map(|&b| b as u16).collect::<Vec<_>>();
    for (rank, &pair) in self.merge_rules.iter().enumerate() {
        token_ids = merge_pair(&token_ids, pair, (256 + rank) as u16);
    }
    token_ids
}
fn decode(&self, token_ids: &[u16]) -> Result<Vec<u8>, String> {
    let mut out = Vec::new();
    for &token_id in token_ids {
        let token = self
            .vocab
            .get(token_id as usize)
            .ok_or("token id outside vocabulary")?;
        if out
            .len()
            .checked_add(token.len())
            .filter(|&n| n <= MAX_DECODE_BYTES)
            .is_none()
        {
            return Err("decoded output exceeds safety limit".to_owned());
        }
        out.extend_from_slice(token);
    }
    Ok(out)
}

4. Save enough information to reproduce token IDs

The reference text format begins with a version header and stores one pair of parent IDs per line. The 256 base entries are implicit. On load, each rule reconstructs the new token bytes by concatenating its parents. The loader rejects an unknown header, malformed numbers, extra columns, and forward references.

Versioning matters because token IDs are model inputs. Changing normalization or merge order while keeping the same model weights silently changes meaning. A language-model checkpoint should identify its tokenizer file and checksum. The chapter project focuses on tokenizer serialization; Chapter 39 checkpoints model and optimizer state.

Normalization is intentionally absent from the byte core. Unicode permits visually similar strings with different byte encodings, and lowercasing rules vary by language. If an application chooses NFC normalization or another transformation, apply it before byte encoding, document its exact version, and test the policy. A reversible tokenizer cannot recover distinctions removed by an earlier normalizer.

Unseen text never needs tokenizer retraining. It falls back to base bytes wherever no merge applies. This guarantees encoding success but may produce longer sequences for languages or domains rare in tokenizer training. Measure bytes per token across each important domain rather than quoting only the training corpus's compression.

Hint 2

Check i + 1 < token_ids.len() before reading the second member.

Answer
fn merge_pair(token_ids: &[u16], pair: (u16, u16), new_token_id: u16) -> Vec<u16> {
    let mut out = Vec::new();
    let mut i = 0;
    while i < token_ids.len() {
        if i + 1 < token_ids.len() && (token_ids[i], token_ids[i + 1]) == pair {
            out.push(new_token_id);
            i += 2
        } else {
            out.push(token_ids[i]);
            i += 1
        }
    }
    out
}

Answer

A token can end halfway through a multi-byte UTF-8 character. Lossy per-token conversion replaces an incomplete prefix before the following token arrives. Concatenate token bytes first, then validate or display the complete sequence.

Worked interpretation

The fitted rule count can be below the requested maximum when no adjacent pair remains twice. Training token count should usually fall as rules are added. Held-out compression may improve less because its frequent pairs differ. Exact round trip must remain true at every setting. Compression says nothing by itself about downstream language-model loss.

6. Review and transfer

From memory, explain why 256 base symbols guarantee coverage, why learned merge order matters, why replacements cannot overlap, and why core decoding returns bytes. Then explain what must be stored beside model weights.

Answers

Every input is a sequence of the 256 byte values. Rules are applied by rank, overlapping replacements would reuse input symbols, and individual tokens may contain incomplete UTF-8 fragments. Store the ordered tokenizer rules, version, and an identity such as a checksum with the model.
