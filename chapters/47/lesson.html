A model can contain many numerical zeros and still occupy the same memory and execute the same multiplications as a dense model. Sparsity becomes useful only when a representation omits those zeros and a kernel follows that representation. This chapter connects a pruning decision to compressed sparse row storage, checks its arithmetic against a dense oracle, and measures rather than assumes performance.

The concrete goal

You will keep weights by magnitude, convert the masked matrix to CSR, run a scalar sparse matrix-vector kernel, verify parity, quantify pruning error, and time dense and sparse kernels at four densities. No speedup is promised in advance.

1. A zero is not yet a saving

Consider a dense layer y=Wx, with W stored in row-major order as [output features, input features]. For four output features and four input features, dense storage reserves sixteen values. A loop visits sixteen positions even if twelve happen to equal zero. The numerical result uses zeros, but the storage and instruction path remain dense.

Sparsity is the fraction of entries that are zero. Density is the fraction that are nonzero, so sparsity+density=1. A matrix with four nonzeros among sixteen entries has density 4/16=0.25 and sparsity 0.75. Always say which quantity you report; “90% sparse” and “density 0.1” describe the same mask.

A structural zero is absent from the sparse representation. A stored zero is still an entry with a value and perhaps an index. Conversion should omit exact zeros. Choosing which small nonzero weights become exact zeros is a separate pruning step.

Separate representation from model change

Let W=[0,2,0; 0,0,0; −3,0,4] and x=[1,2,3]. Dense multiplication gives y=[0×1+2×2+0×3, 0, −3×1+0×2+4×3]=[4,0,9]. A correct sparse encoding must reproduce [4,0,9] exactly apart from floating-point accumulation. That comparison says the representation is correct. It says nothing about whether turning an earlier weight into zero preserved task quality.

2. Choose a mask with magnitude pruning

Magnitude pruning ranks weights by absolute value and removes the smallest. Given [−1.0, 0.2, 3.0, −2.0] and target density 0.5, keep two entries. Their magnitudes rank 3.0, 2.0, 1.0, 0.2, so the masked vector is [0,0,3.0,−2.0]. The negative sign of −2 does not make it small.

The project uses a global budget: round(density × number_of_weights) entries survive across the whole matrix. It sorts indices by descending absolute magnitude and breaks exact ties by original index. This deterministic rule makes tests repeatable. Layer-wise budgets, percentile thresholds, and structured pruning remove different patterns and answer different design questions.

let keep = (density * weights.len() as f64).round() as usize;
order.sort_by(|&i, &j| weights[j].abs().total_cmp(&weights[i].abs())
    .then_with(|| i.cmp(&j)));
for &index in &order[..keep] {
    mask[index] = true;
}

Why might magnitude work? Near a particular parameter setting, setting a small weight to zero changes that parameter by a small amount. But network sensitivity depends on inputs, interactions, normalization, and later nonlinearities. Magnitude is a heuristic, not a proof of harmlessness.

Published pruning pipelines commonly train a dense network, prune, and retrain surviving weights while preserving the mask. This chapter uses a deterministic untrained matrix so representation and timing are visible without a long training dependency. It computes output root mean square error against the unpruned matrix as density falls. That output error is real for the fixture, but it is not an accuracy score.

Two comparisons answer different questions.

Masked dense versus CSR checks implementation parity. Unpruned dense versus pruned output measures the numerical change caused by pruning. Comparing CSR only with its masked source can prove the kernel correct while a real model has lost unacceptable quality.

3. Encode rows with CSR

Compressed sparse row stores three arrays. values holds nonzero values in row order. col_idx holds each value's original column. row_ptr has rows+1 offsets. Row r occupies the half-open range row_ptr[r]..row_ptr[r+1].

For the worked matrix, values=[2,−3,4], col_idx=[1,0,2], and row_ptr=[0,1,1,3]. Row zero uses entry 0. Row one uses the empty range 1..1. Row two uses entries 1..3. The last pointer is three, equal to the nonzero count.

y[r] = Σk=row_ptr[r]..row_ptr[r+1] values[k] × x[col_idx[k]]

The Rust conversion scans each dense row and pushes only values unequal to zero. It appends the current value count after every row, including empty rows. The matrix constructor rejects zero dimensions, mismatched shape products, and nonfinite values. The matvec method checks the input length and finiteness before following column indices.

for row in dense.chunks_exact(cols) {
    for (column, &value) in row.iter().enumerate() {
        if value != 0.0 {
            col_idx.push(column);
            values.push(value);
        }
    }
    row_ptr.push(values.len());
}

CSR saves value storage only by adding indices. With f64 values and 64-bit usize indices, each nonzero consumes roughly sixteen bytes across values and columns, plus row pointers. A dense f64 consumes eight bytes per position. The storage crossover can therefore require density substantially below one half on this representation. Cache behavior and allocator overhead add more detail.

Count the bytes before timing

For R rows, C columns, and K stored values, dense payload is 8RC bytes with f64. On a machine with eight-byte usize, CSR payload is 8K for values, 8K for columns, and 8(R+1) for row pointers: 16K+8(R+1). These are logical array payloads, excluding vector headers and unused allocation capacity. For our 3×3 worked matrix, dense needs 72 bytes while CSR needs 48+32=80 bytes. It has only three nonzeros, yet the row pointers make it larger. For the 192×192 fixture at K=7,373, dense needs 294,912 bytes and CSR needs 119,512. The larger problem amortizes pointer overhead.

Storage and arithmetic also differ in how they depend on the input. Let ΔW=W−Wpruned be the removed matrix. The output change is Δy=ΔW x. Within one output row, removed positive and negative products may cancel. Removing still more weights can accidentally improve one input's output error even as the matrix approximation worsens. That explains why the default sweep can report slightly lower RMSE at density 0.05 than at 0.2. A real evaluation therefore needs many representative held-out activations or task examples, followed by the same downstream metric used before pruning. One sinusoidal input is a useful arithmetic probe, not a substitute for that evaluation.

Matrix-vector multiplication is often limited by memory movement. CSR skips multiply-adds but loads an index and gathers an input value indirectly. Short irregular rows can reduce locality or load balance. Small matrices can spend more time on branches and setup than they save. Format and hardware determine whether zeros become time savings.

4. Build a fair kernel measurement

A kernel benchmark times only the numerical loop under comparison. The project generates and prunes the matrix, converts CSR, and allocates both output buffers before timing. Each kernel is warmed once. Then it runs 31 samples on the same f64 input and reports median, minimum, and maximum duration.

The output buffer is reused. Otherwise allocating a vector inside each CSR timing could dominate small kernels and turn an allocation comparison into a matrix-format claim. std::hint::black_box consumes the outputs so the optimizer has less freedom to erase unused work. Rust documents this barrier as best effort, so it does not replace inspection or a mature benchmark harness.

Use release mode. Debug builds include bounds checks and skip many optimizations, as the program prints through release=false. Record matrix shape, numeric type, processor, compiler, flags, and nonzero pattern before comparing machines. The default output labels timings as dense-kernel and CSR-kernel medians; sorting, pruning, CSR construction, allocation, and printing lie outside.

A numerical parity check precedes every timing. For output elements a and b, the allowed difference is 10−10 + 10−8max(|a|,|b|). Nonfinite values fail rather than passing through infinite tolerance. Different reduction order can change last digits even when both kernels are correct.

Read a density row honestly

Suppose a run says density 0.200, 7,373 nonzeros, pruning-output RMSE 2.4, dense median 20 μs, and CSR median 12 μs. It means CSR was faster for this matrix-vector kernel on this run while changing the unpruned output by RMSE 2.4. It does not include conversion, say whether 2.4 is acceptable for a task, or predict a batched GPU layer.

Exercise A · Build row pointers

Open ch47_01.rs. The three rows have one, zero, and two nonzeros.

Hint 1 · Required length

Start with zero. Append one cumulative count for every row, so the answer has four entries.

Hint 2 · Empty row

An empty row repeats the previous offset; it does not disappear.

Worked solution
let mut result = vec![0];
for row in rows {
    let count = row.iter().filter(|&&x| x != 0.0).count();
    result.push(result.last().copied().unwrap_or(0) + count);
}

The final result is [0,1,1,3].

Debugging · Sparse appears slower at every density

A benchmark calls csr.matvec, which allocates a new vector, but the dense code reuses an output slice. It also converts CSR inside each timed sample. Explain the result.

Answer

The experiment includes allocation and conversion only in the sparse path, so it does not isolate kernels. Prebuild CSR, allocate both outputs before timing, warm both paths, and use in-place kernels. Measure conversion separately if end-to-end latency matters. CSR may still be slower afterward; that would then be evidence about this workload.

Independent variation · Structured rows

Keep the same nonzero count but place surviving values into a contiguous band in each row instead of global magnitude positions. Run parity and timings again.

Worked answer

Parity should still hold if CSR encodes the same masked matrix. Timing may change because column access becomes more local and row lengths more regular. Pruning error can also change because the mask no longer selects by magnitude. Density alone therefore cannot describe either quality or execution cost.
