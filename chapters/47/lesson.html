Which weights survive a fixed budget?

Take weights [−1,0.2,3,−2] and retain half the positions. Rank absolute magnitudes 3,2,1,0.2, so the result is [0,0,3,−2]. A negative sign does not make a weight unimportant. For density d and N positions, this lab retains round⁡(d×N) positions globally. Exact magnitude ties retain the lower original index; with [2,−2] and one survivor, keep [2,0].

It is tempting to sort the values themselves. That would destroy which input coordinate each weight multiplies. Sort indices, build a mask of original positions, and preserve the order of the output vector. Validation remains supplied: weights are nonempty and finite, and requested density lies in [0,1]. The mask need not create that many nonzeros if the input already contains exact zeros.

Why magnitude at all? Removing a small weight makes a small parameter change, but the effect on a prediction also depends on its input. Removing weight 0.01 on input 1000 changes a linear output by 10; removing weight 1 on input 0 changes it by 0. Magnitude is a useful heuristic, not a sensitivity proof. Real pruning commonly follows dense training and is followed by retraining surviving weights; this experiment isolates the mask and execution mechanics.

For a removed matrix ΔW=W−Wpruned, the output change is Δy=ΔWx. Signed removed products can cancel. Consequently one input’s error need not grow monotonically as more positions are removed. Preserve both comparisons: unpruned versus pruned for change in function; masked dense versus sparse for implementation correctness.

How can an empty row exist without stored zeros?

Recall the first result [4,0,9]. Compressed sparse row, or CSR, stores three arrays: values=[2,-3,4], col_idx=[1,0,2], and row_ptr=[0,1,1,3]. The column index says which input to multiply. The row pointers say where each output row’s stored entries begin and end.

Row r occupies the half-open interval row_ptr[r]..row_ptr[r+1]. The middle row occupies 1..1, an empty interval; its sum is 0. The final pointer equals the number of stored values, so there are rows+1 pointers. Conversion scans original rows, pushes only exact nonzeros and their columns, and appends the current stored count after every row. It must not apply an extra magnitude threshold.

The kernel is a sum over stored positions k: 

y[r] += values[k] * x[col_idx[k]];

For the last row, k=1 multiplies −3 by x[0]=1; k=2 multiplies 4 by x[2]=3. The result is 9. Using x[k] instead of x[col_idx[k]] confuses a compressed address with the original input coordinate.

Predict before coding: if the input becomes [−2,0.5,1.5], the result becomes [1,0,12]. This unfamiliar signed probe is in the local goal check. It catches a kernel that reproduces [4,0,9] by memorizing the example rather than following the column indices.

When do fewer values save bytes or time?

On a machine with eight-byte usize, a dense f64 matrix with R rows and C columns uses 8RC payload bytes. CSR with K nonzeros uses 8K value bytes, 8K index bytes, and 8(R+1) row-pointer bytes. For our 3×3 example, dense is 72 bytes and CSR is 48+32=80 bytes. It is sparse yet larger. Vector headers and spare capacity are excluded from both payload counts.

At 192×192 and K=7373, dense is 294912 bytes and CSR is 119512. The row-pointer overhead is spread over many more positions. Use std::mem::size_of::<usize>() when calculating your own machine’s index payload. The crossover is a property of representation and dimensions, not a universal “50% sparse” rule.

Time is another measurement. A sparse kernel skips multiplications but reads indices and gathers inputs indirectly. Locality, irregular row lengths, SIMD, batching, and GPU formats can change the outcome. Run just lab 47 only after parity is correct.
