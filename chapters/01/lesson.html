A program usually follows rules you write. A learning program adjusts a few numbers so that its predictions fit examples. In this chapter, you will write that adjustment yourself—and watch one artificial neuron learn a rule you never put into its training function.

Your first milestone

By the end, a small Rust program will learn a straight line from five examples, then predict an answer for an input it did not train on. You need functions, loops, and basic arithmetic. You do not need calculus or an ML library.

1. Start with examples, not machinery

Imagine a sensor whose raw reading needs to be converted to a calibrated measurement. You could write a conversion formula if you knew it. Suppose instead that someone gives you five pairs of raw readings and trusted measurements. Your job is to infer a useful conversion from these pairs.

A dataset is a collection of examples. Each example here has one input, x, and one desired answer, y. The desired answer is called a target. Because the examples include answers, this is supervised learning. “Supervised” describes the available labels; it does not mean a person must adjust the model after every prediction.

You may already see the pattern: double x and add one. That is intentional. A problem with a known answer lets us check the learning procedure before trusting it on anything complicated. Our training code will receive the pairs above, not a special instruction to choose two and one.

Real sensor data contains noise and may not follow a straight line. We will study those complications later. The first task is narrower: establish exactly what “learn from examples” means. Do not confuse a useful teaching fixture with evidence that a model will work on a real sensor.

Each tuple stores an input and target. We use f64, Rust's double-precision floating-point type, so tiny numerical changes are easier to observe. Floating-point arithmetic approximates real arithmetic; later chapters will explain why precision and rounding matter.

2. A neuron is a small computation

Our model makes a prediction by multiplying the input by a weight and adding a bias:

ŷ = wx + b

The hat in ŷ means “predicted,” distinguishing our guess from the target y. The weight w controls how much the prediction changes when x changes. The bias b shifts every prediction by the same amount. These two adjustable values are the model's parameters.

This is a scalar artificial neuron with an identity activation: its weighted sum is returned unchanged. Other neurons apply an extra function to that sum. We will add those functions when a straight-line predictor is no longer expressive enough. An artificial neuron is a mathematical building block; it is not a detailed simulation of a biological cell.

Trace one prediction

Set w = 0.5 and b = 1. For x = 2, the prediction is 0.5 × 2 + 1 = 2. The target is 5, so the prediction is too low by 3. If we change the weight to 2 while keeping b = 1, the prediction becomes 5.

Check a second point before declaring success. At x = −1, that same model predicts 2 × (−1) + 1 = −1, also matching the target. A model is one shared rule applied to every example, not a separate answer stored for each row.

A Rust struct groups values that belong together. Here Neuron stores the two parameters:

#[derive(Clone, Copy, Debug)]
struct Neuron {
    weight: f64,
    bias: f64,
}

An impl Neuron block attaches operations to this type. In an inspecting method, &self borrows the current neuron so the method can read its parameters without taking ownership or changing them:

fn predict(&self, input: f64) -> f64 {
    self.weight * input + self.bias
}

This definition appears inside impl Neuron. A call therefore reads model.predict(input): the receiver before the dot supplies &self, and the scalar in parentheses supplies input.

Running this calculation with fixed parameters is inference. Inference does not change the model. Training is the separate procedure that changes its parameters using examples. Keeping those two operations distinct will matter when models get large.

3. Give a wrong answer a number

To choose better parameters, we need a way to compare guesses. A loss assigns a number to the model's errors. Smaller is better. For one example, subtract the target from the prediction and square the result. Squaring prevents positive and negative errors from cancelling.

For a dataset of N examples, we average the squared errors. This is the mean squared error, often abbreviated MSE:

L(w, b) = (1/N) Σᵢ (wxᵢ + b − yᵢ)²

The symbol Σ means “sum these terms.” The index i visits each example. Here N = 5. L is a function of the parameters because changing w or b changes the predictions and therefore changes the loss. The inputs and targets remain fixed during this calculation.

Calculate the starting loss

Start with w = 0 and b = 0. Every prediction is zero. The squared errors are 9, 1, 1, 9, and 25. Their sum is 45; dividing by five gives a loss of 9.

Now try w = 1 and b = 0. The predictions are −2, −1, 0, 1, 2. Their errors are 1, 0, −1, −2, −3; the squared errors sum to 15. The new loss is 3. This change improved the model even though it did not solve the task.

Fallible methods return Result<value, error>. Ok(value) means the calculation succeeded; Err(message) explains invalid or nonfinite data. The ? operator unwraps an Ok value and immediately returns an Err to the caller. This keeps error handling visible without repeating a match after every loss calculation.

fn loss(&self, data: &[(f64, f64)]) -> Result<f64, &'static str> {
    if data.is_empty() {
        return Err("loss requires at least one example");
    }
    if !self.weight.is_finite()
        || !self.bias.is_finite()
        || data.iter().any(|(input, target)| !input.is_finite() || !target.is_finite())
    {
        return Err("model and examples must contain finite numbers");
    }
    let loss = data
        .iter()
        .map(|&(input, target)| (self.predict(input) - target).powi(2))
        .sum::<f64>()
        / data.len() as f64;
    if !loss.is_finite() {
        return Err("loss overflowed; reduce input scale or learning rate");
    }
    Ok(loss)
}

The complete project checks that the dataset is not empty before dividing by its length. It also rejects nonfinite inputs and overflowing loss values. Those checks are practical parts of numerical programming: a NaN, meaning “not a number,” can otherwise travel through every later calculation.

MSE is not the only loss. It is useful here because our target is a number and we want predictions close to it. Choosing a loss expresses what errors the training procedure should care about. Classification and language modeling will require different choices.

4. Let the computer find a better direction

We could try many pairs of weights and biases, but an exhaustive search becomes expensive as the number of parameters grows. A more useful question is local: if I change this parameter a tiny amount, does the loss rise or fall?

Hold b fixed and calculate the loss once at w + h and once at w − h, where h is a small positive number. The difference in loss divided by the distance between these two weights estimates the slope:

gw ≈ [L(w + h, b) − L(w − h, b)] / (2h)

Do the same for b while holding w fixed. Together, these slopes form a gradient: one slope for each adjustable parameter. A positive slope says the loss rises when that parameter increases; a negative slope says it falls. This central-difference calculation is a numerical estimate, not an exact symbolic derivative.

A separate Gradient struct stores these two slopes. Its fields correspond to the neuron’s parameters, but contain derivatives rather than learned values:

#[derive(Clone, Copy, Debug)]
struct Gradient {
    weight: f64,
    bias: f64,
}
fn numerical_gradient(&self, data: &[(f64, f64)]) -> Result<Gradient, &'static str> {
    const H: f64 = 1e-5;
    let weight = (Self {
        weight: self.weight + H,
        ..*self
    }
    .loss(data)?
        - Self {
            weight: self.weight - H,
            ..*self
        }
        .loss(data)?)
        / (2.0 * H);
    let bias = (Self {
        bias: self.bias + H,
        ..*self
    }
    .loss(data)?
        - Self {
            bias: self.bias - H,
            ..*self
        }
        .loss(data)?)
        / (2.0 * H);
    if !weight.is_finite() || !bias.is_finite() {
        return Err("numerical gradient overflowed; reduce input scale");
    }
    Ok(Gradient { weight, bias })
}

The returned Gradient names each slope after its parameter. Each temporary Self changes exactly one field by H; ..*self copies the other field from the unchanged borrowed model. The four loss(data)? calls all use the same examples and propagate any validation error.

We move against the slopes to reduce the loss. A positive learning rate η controls the size of that move:

wnew = w − ηgw    bnew = b − ηgb

This procedure is called gradient descent. “Descent” describes movement toward smaller loss. A step that is too large can jump over a useful region and make the loss worse. There is no guarantee that an arbitrary learning rate works just because the slope calculation is correct.

The first complete training step

For this symmetric dataset, expanding the squared errors gives L(w,b) = 2(w−2)² + (b−1)². You do not need to derive that expression yet; use it to check the numbers.

At w = 0, b = 0, the numerical slopes are approximately −8 and −2. With η = 0.1, the new weight is 0 − 0.1 × (−8) = 0.8 and the new bias is 0.2. The new loss is 2 × (0.8−2)² + (0.2−1)² = 3.52. One step reduced the loss from 9 to 3.52.

Compute both slopes from the same old model, then update both parameters. If you update w before estimating the slope for b, you have changed the algorithm. Our reference code makes the distinction explicit by calculating a new model from an unchanged copy.

This update method takes self and returns Self, the same type Neuron. It constructs a new model from the old parameters and the complete gradient:

fn step(
    self,
    data: &[(f64, f64)],
    learning_rate: f64
) -> Result<Self, &'static str> {
    if !learning_rate.is_finite() || learning_rate <= 0.0 {
        return Err("learning rate must be finite and positive");
    }
    let gradient = self.numerical_gradient(data)?;
    let next = Self {
        weight: self.weight - learning_rate * gradient.weight,
        bias: self.bias - learning_rate * gradient.bias,
    };
    next.loss(data)?;
    Ok(next)
}

self is still available after numerical_gradient because that method only borrows it. Both fields of next therefore use the same old parameters and the same Gradient. The final next.loss(data)? rejects an update that produced a nonfinite result before returning Ok(next).

We use h = 0.00001. Smaller is not always better: subtracting nearly equal floating-point numbers can lose useful precision. Central differences are excellent for understanding and checking gradients, but they require separate loss evaluations for each parameter. Chapter 2 derives a cheaper analytical update; later, backpropagation makes gradients practical for millions of parameters.

Use the interactive experiment above to compare learning rates. At 0.01 the line moves cautiously. At 0.1 it approaches the data rapidly. At 0.6 the weight oscillates and diverges on this dataset. Observe the numerical loss as well as the picture: a line leaving the plotting area is a symptom, not an explanation.

Its Neuron stores two numbers. predict performs inference, loss evaluates the dataset, numerical_gradient returns a separate Gradient, and step returns one updated model. The train method receives the actual dataset and repeats that step 100 times:

fn train(
    self,
    data: &[(f64, f64)],
    steps: usize,
    learning_rate: f64,
) -> Result<Self, &'static str> {
    if !learning_rate.is_finite() || learning_rate <= 0.0 {
        return Err("learning rate must be finite and positive");
    }
    self.loss(data)?;
    let mut model = self;
    for _ in 0..steps {
        model = model.step(data, learning_rate)?;
    }
    Ok(model)
}

Debugging · The loss gets larger

A learner writes weight += learning_rate * slope. The model starts at zero and the first weight becomes −0.8. Explain the bug before changing the code.

Answer

The estimated slope at zero is negative, so increasing the weight would lower the loss. Adding the negative slope instead decreases the weight: this climbs uphill. Subtract the slope. Still check the learning rate, because a correct sign does not prevent overshooting.

Independent variation · Learn a different line

Create examples with targets from y = −0.5x + 3, keeping the same five input values. Without changing the training algorithm, learn new parameters and predict at x = 0.5. Write your expected answer before running.

Worked answer

The targets become 4, 3.5, 3, 2.5, 2. The learned weight should approach −0.5 and the bias 3. The held-out prediction should approach −0.5 × 0.5 + 3 = 2.75. If your implementation still returns the old line, look for hard-coded targets or parameters.

The weight and bias change; the supplied training pairs stay fixed. Squaring stops signed errors cancelling and gives larger errors more influence. A negative slope means a small increase in that parameter lowers the loss locally. Inference applies fixed parameters, whereas training changes them using a loss.
