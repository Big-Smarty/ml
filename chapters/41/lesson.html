The cache from Chapter 40 removes repeated activation work, but a decoder must still read its weights for every token. Quantization stores approximate weights with small integers. This chapter implements signed int8 and genuinely packed int4 weights, dequantizes them during matrix-vector multiplication, and measures storage, numerical error, decoder loss, and local runtime separately.

Milestone

You will pack two signed four-bit values into one byte, run both formats through a real matrix-vector kernel, replace the Chapter 36 decoder’s output projection with dequantized weights, and inspect what changed.

1. Map real weights onto a finite grid

A floating-point output row can represent many magnitudes. A signed b-bit integer has a much smaller set. Our symmetric weight quantization accepts row-major weights [out_features,in_features], chooses one scale s for each output row, then maps a real weight w to q = clamp(round(w/s), −qmax, qmax). For int8, qmax = 127; for signed int4, qmax = 7. Reconstruction is ŵ = sq.

The scale is max|w| / qmax for that row. Every row therefore uses its integer range around its own largest magnitude. A single scale for a whole matrix would be cheaper metadata, but one outlier could make the grid coarse for every other row. An all-zero row uses scale one and stores zeros. The implementation also prevents a nonzero subnormal scale from rounding to zero.

Quantize one dot product

Let x = [1.2, −0.7] and w = [0.5, −1.1]. With the weight scale s = 1.1/127 ≈ 0.008661, the codes are [58, −127]. Dequantized weights are about [0.5024, −1.1]. Their dot product is 1.2×0.5024 + (−0.7)×(−1.1) ≈ 1.3728; the dense answer is 1.37. The difference comes from rounding 0.5 to the nearest grid point.

The complete scalar f32 reference uses the same argument order in the reference project and starter:

fn dense_matvec_reference(
    weights: &[f32],
    out_features: usize,
    in_features: usize,
    input: &[f32],
) -> Vec<f32> {
    (0..out_features)
        .map(|r| {
            (0..in_features)
                .map(|c| weights[r * in_features + c] * input[c])
                .sum()
        })
        .collect()
}

This project keeps activations in f32. At multiplication time it converts each integer weight to f32 with its row scale, multiplies by the activation, and accumulates in f32. That is weight-only quantization. Integer-only inference also quantizes activations, normally accumulates products in a wider integer such as int32, and rescales the result. Do not describe this kernel as integer-only.

2. Put two int4 weights in one byte

Rust has no ordinary four-bit integer type. We store the low four bits of one signed i8 in the byte’s low nibble and the low four bits of the next in the high nibble. Values −8 through 7 use four-bit two’s-complement form. Our symmetric quantizer emits only −7 through 7; the packing format can represent −8, but that asymmetric extra level is unused. When unpacking, a nibble with bit 3 set is sign-extended by filling its upper four bits with ones.

fn pack_int4_pair(low: i8, high: i8) -> u8 {
    (low as u8 & 0x0f) | ((high as u8 & 0x0f) << 4)
}

Read a packed byte

Store −1 and 3. Their low nibbles are 1111 and 0011, so the packed byte is 0011_1111, hexadecimal 0x3f. Reading the low nibble gives 15; because its sign bit is set, sign extension recovers −1. Reading the high nibble gives 3. If the total R×C weight count is odd, the unused final high nibble is zero and matrix dimensions prevent it from being read.

The reference implementation stores raw codes plus one f32 scale per output row. For weights [out_features,in_features], let R=out_features and C=in_features. Int8 uses RC bytes plus 4R metadata bytes. Packed int4 uses ceil(RC/2) plus 4R bytes. “Four-bit model” is therefore shorthand: scales, biases, embeddings, normalization parameters, alignment, and file headers add storage.

A production format may quantize blocks rather than rows, store minima or zero points, reorder nibbles for a kernel, or use data-aware rounding. Packed layout and mathematical quantization format are separate design decisions. The decoder comparison deliberately transposes its [D,V] output matrix to [V,D], applies one scale per vocabulary output, then transposes the dequantized values back.

3. Evaluate quantization error and model loss separately

Compression is observable before model evaluation. The default 3×6 fixture occupies 72 bytes as f32 weights. Including row scales, int8 occupies 30 bytes and packed int4 occupies 21. Those ratios are exact for this tiny format; metadata becomes a smaller fraction for wider rows.

quantization_error reports two views of numerical approximation. Root-mean-square error is sqrt[(1/N)Σ(yᵢ−ŷᵢ)²], where N is the number of compared output coordinates. Maximum absolute error reports the worst coordinate. The fixture’s measured int8 RMSE is 0.016789 and its int4 RMSE is 0.143561. Int4 saves more storage and has more quantization error here because its grid has only fifteen symmetric levels.

Small quantization error does not directly equal model quality. The project clones the actual Chapter 36 decoder, quantizes only its [D,V] vocabulary projection through the [V,D] row view described above, and evaluates the same input token IDs and targets. It prints full-logit maximum error, mean next-token cross-entropy loss, and the last-position argmax. That cross-entropy is the model’s loss, not a quantization-error statistic, and no training occurs. For this comparison the code writes reconstructed [D,V] f32 values back into a dense decoder clone; it evaluates quantization error through the real model but does not execute the packed kernel inside the decoder. Agreement on one token can hide changes elsewhere in the distribution; loss can change without changing that argmax.

Diagnose a false quality claim.

A learner reports “int4 is accurate because the generated token stayed 6.” That observes one decision on one prefix. Check logit error and loss across a held-out prompt set, then task metrics appropriate to the model. A training fixture measures memorization if it was used to choose scales or quantization corrections. Our random tiny decoder is a mechanism check, not evidence about a trained language model.

4. Storage savings do not promise speed

Fewer bytes can reduce memory traffic, which matters when weight reads dominate generation. Yet the bundled kernel unpacks and dequantizes each value in a scalar Rust loop. It has no vector instructions, fused dot-product instruction, threading, or hardware-specific packed layout. Int4 may therefore be slower than dense f32 despite occupying fewer bytes.

Run the optional benchmark with --bench. It warms each path, measures seven samples of 200 fixed 256×256 matrix-vector products, reports the median, exposes every complete output vector to the optimization barrier, and retains a checksum. Each call allocates its output vector, so these times include allocation as well as arithmetic. The result belongs to your CPU, compiler, build, dimensions, and this kernel. Compare fp32, int8, and int4 medians; do not transplant a paper’s accelerator speedup.

Dequantization can occur ahead of time, inside a fused kernel, or in registers as packed values are loaded. Ahead-of-time conversion loses runtime storage-bandwidth benefits. A fused kernel is more complex but avoids materializing a full f32 matrix. The course implementation chooses direct clarity: read code, multiply by the scale, and accumulate.

Quality and performance also respond to different knobs. Smaller quantization groups often reduce quantization error but add metadata and scale loads. Quantization-aware training can adapt parameters to the grid, whereas this chapter performs deterministic post-training rounding. Hardware support decides whether smaller codes translate into faster arithmetic.

Worked answer
fn pack_int4_pair(low: i8, high: i8) -> u8 {
    (low as u8 & 0x0f) | ((high as u8 & 0x0f) << 4)
}

Mask both values with 0x0f, shift the second left four bits, and combine with bitwise OR. For (−1,3), the answer is 0x3f.

Debugging · Every small row becomes zero

A matrix uses one global scale determined by an outlier of magnitude 1000. Most weights are near 0.01 and round to zero. Explain the cause and repair.

Answer

The global grid spacing is roughly 1000/127 for int8, far larger than ordinary weights. Use per-row or smaller-group scales, or handle the outlier separately. More scales cost metadata; evaluate the resulting model rather than assuming the repair is sufficient.

Independent variation

Change the linear fixture to 4×9. Before running, calculate fp32, int8, and int4 weight-plus-scale bytes.

Answer

There are 36 weights: fp32 is 144 bytes. Int8 is 36 code bytes plus 16 scale bytes = 52. Int4 is 18 packed bytes plus 16 scale bytes = 34. Alignment is not included in this vector-based format.
