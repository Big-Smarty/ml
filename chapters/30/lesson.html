Which neighboring values must one result use?

Eight numbers [3,1,4,1,5,9,2,6] must become one sum, 31. A matrix multiplication must reuse values while preserving [58,64,139,154]. Run just lab 30: the direct CPU loops already produce both answers. On hardware, the baseline uses serial subtotals and independent dot products. Your goal is to preserve those answers while making neighboring invocations cooperate.

Recall Chapter 29: one output had one owner and needed no neighbor. A sum's final owner needs contributions from other lanes. A matrix tile can let multiple output owners reuse the same loaded values. Shared storage creates two new questions: who writes each value, and when may others read it?

The learner entry is ch30.rs. MATMUL and REDUCE are real WGSL strings compiled by the same supplied host. CPU matmul and reduce are always available. The original ch30 library remains the independent row-major oracle and the stable API used by later reference projects.

Shapes before formulas

A=[[1,2,3],[4,5,6]] has 2 rows of 3 numbers. B=[[7,8],[9,10],[11,12]] has 3 rows of 2 numbers. Output[0,0] pairs A's first row with B's first column: 1×7 + 2×9 + 3×11 = 58. Reuse the same row with the second column to get 64. In general A[m,k] times B[k,n] gives C[m,n]; k counts the products added for each output. This is GEMM, or general matrix multiplication. We will first learn cooperation with a sum.

Combine values with a shared reduction tree

Consider eight values [3, 1, 4, 1, 5, 9, 2, 6]. Put one value in each shared slot. At stride four, lanes 0–3 add slots 4–7, producing [8, 10, 6, 7]. At stride two, lanes 0–1 produce [14, 17]. At stride one, lane 0 produces 31. Three synchronized levels replace seven serial additions with parallel stages.

stride: 4 → 2 → 1   |   active lanes: 4 → 2 → 1   |   result: 31

The WGSL kernel allocates var<workgroup> scratch: array<f32, 256>. This workgroup memory is visible to all 256 lanes in this group and to no other group. Each lane stores either its input or zero. Zero is the additive identity: x + 0 = x, so an absent edge value changes nothing.

Every stage ends with workgroupBarrier(). The barrier ensures all writes are visible before the next reads. It must occur in uniform control flow. An out-of-range lane cannot return early; other lanes could wait for it forever. Edge lanes write zero and reach every barrier.

let first = group.x * 512u + lane;
let second = first + 256u;
scratch[lane] = 0.0;
if (first < dispatch_params.element_count) { scratch[lane] = input[first]; }
if (second < dispatch_params.element_count) { scratch[lane] += input[second]; }
workgroupBarrier();

The reduction kernel's workgroup size is [256,1,1]. For a stage with L inputs, Rust dispatches [ceil(L/512),1,1] workgroups, so the global grid contains 256×ceil(L/512) invocations. Each invocation conditionally loads two positions, which is why one workgroup consumes up to 512 values. dispatch_params.element_count is L for the current stage, not the original N forever.

Larger arrays produce one subtotal per workgroup, changing the shape from [L] to [ceil(L/512)]. A 777-value input becomes [2] and then [1]. workgroupBarrier() orders the 256 lanes inside one group only; it cannot synchronize different groups. Rust therefore ends that compute pass and starts the next ordered pass over the subtotal buffer. That pass boundary supplies the required device-wide stage ordering.

The scalar pair uses the same finite, nonempty input boundary and sums in ordinary slice order:

pub fn reduce_sum_scalar(values: &[f32]) -> Result<f32, Box<dyn Error>> {
    validate_reduction_values(values)?;
    Ok(values.iter().sum())
}

Reuse one loaded tile across output owners

A 16×16 workgroup owns one 16×16 output tile. Local lane (y,x) computes one output at row group.y*16+y and column group.x*16+x. All 256 lanes cooperatively load A tile [16,16] and B tile [16,16] into two workgroup arrays. The tile's first axis follows output rows for A and the shared inner axis for B; its second axis follows the shared inner axis for A and output columns for B. After a barrier, every lane performs sixteen multiply-adds using those values.

let row = group.y * 16u + local.y;
let col = group.x * 16u + local.x;
let lane = local.y * 16u + local.x;
let tile_count = (shape.k + 15u) / 16u;
var sum = 0.0;

Rust dispatches [ceil(n/16), ceil(m/16), 1] workgroups: x covers C columns and y covers C rows. Multiplying by the local size gives a padded global grid of [16×ceil(n/16), 16×ceil(m/16), 1] invocations. The shader reconstructs row and col from workgroup and local IDs instead of using global_invocation_id. Workgroup coordinates choose an output tile; local coordinates choose one C element inside it.

group (x,y) selects one C tile
local (x,y) selects one C element
load A/B tiles → barrier → dot products → barrier → next K tile

For k = 17, two tile rounds are required. The first covers inner indices 0–15. The second covers index 16 plus fifteen absent positions. Those positions load zero. Crucially, WGSL's select(zero, array[index], condition) is not a bounds guard because both value expressions are evaluated. The shader uses explicit if statements before indexed reads.

A 2×3 by 3×2 product

Let A = [[1,2,3],[4,5,6]] and B = [[7,8],[9,10],[11,12]]. Then C0,0 = 1×7 + 2×9 + 3×11 = 58; C0,1 = 64; C1,0 = 139; C1,1 = 154. The program prints [58, 64, 139, 154] in contiguous row-major order.

A second barrier after accumulation prevents a fast lane from loading the next tile over shared values that a slower lane still reads. Barriers solve ordering inside a workgroup. Separate workgroups remain independent, which is safe because each owns distinct output positions.

Which addresses remain valid at an edge?

This signature is an exact excerpt from the impl Gpu block:

pub fn matmul(
    &self,
    a: &[f32],
    b: &[f32],
    m: usize,
    k: usize,
    n: usize,
) -> Result<Vec<f32>, Box<dyn Error>>

It rejects zero dimensions, checked-product overflow, mismatched slice lengths, nonfinite entries, sizes beyond WGSL's u32 indexing, sizes beyond the device's maximum buffer or storage binding, and dispatch counts beyond the device limit. Validation occurs before buffer creation. This turns caller-controlled shapes into ordinary errors instead of wgpu validation failures.

The method dispatches ceil(n/16) groups across x and ceil(m/16) groups across y. For m = 3 and n = 5, one group launches 256 lanes but only fifteen final stores are valid. Every lane still participates in all tile loads and barriers. The output guard controls only the final storage write.

For m = 17 and n = 33, the grid is three groups across and two down. This exercises full and partial output tiles simultaneously: the last column group owns only one valid column, while the last row group owns only one valid row. Combined with k = 19, it also exercises a partial inner tile. A test with only small output dimensions can check K padding yet miss workgroup-coordinate or output-stride errors, so the hardware test includes this larger rectangular case.

Gpu::new stores the device, queue, both pipelines, and limits. Later calls reuse them. Each current Gpu::matmul call still uploads A and B and reads C, so its wall time includes transfers. Later decoder integration can use this correct bridge without claiming full model residency.

Trace row-major addresses

The shader never sees a two-dimensional Rust array. For A, address (row,t) becomes row*k+t; for B, address (t,col) becomes t*n+col; for C it becomes row*n+col. Using m as the B stride is a common bug that square matrices conceal. The nonsquare fixtures make every stride distinct enough to expose that mistake.

Take A shaped [3,17] and B shaped [17,5]. A contains 51 values, B contains 85, and C contains 15. C[2,3] is stored at 2×5+3 = 13. During the second K tile, only inner index 16 is real. A lane loading A[2,16] uses offset 50. A lane loading B[16,3] uses offset 83. Both are valid; neighboring tile positions with inner index 17 are zero-filled.

Why the host checks hardware limits

Checked multiplication only proves the dimensions fit a CPU usize. WGSL indices in this shader are u32, and each adapter advertises storage binding, buffer, and dispatch limits. The library checks all of them before asking wgpu to allocate. This matters because wgpu validation errors may otherwise surface asynchronously or panic at resource creation, which is a poor response to caller-controlled dimensions.

Keep the scalar oracle beside the GPU method

matmul_scalar accepts the same slices and dimensions, performs the same shape, length, and finiteness validation, and returns the same row-major shape. Gpu::matmul additionally checks device buffer and dispatch limits. The scalar oracle's direct row-col-inner traversal makes it easy to inspect. Gpu::matmul changes data movement and accumulation grouping, not the mathematical operation.

let mut c = vec![0.0; c_len];
for row in 0..m {
    for col in 0..n {
        c[row * n + col] = (0..k)
            .map(|inner| a[row * k + inner] * b[inner * n + col])
            .sum();
    }
}
Ok(c)
Floating-point sums may differ.

The tiled kernel accumulates in a different order from some CPU implementations, and hardware may fuse multiply-add. The oracle comparison uses absolute tolerance 1e−5 plus relative tolerance 1e−4 times the expected magnitude. Bitwise equality is not portable.
