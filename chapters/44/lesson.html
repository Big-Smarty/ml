Fine-tuning can shape behavior, but it is a poor way to update every fact. Retrieval-augmented generation first searches an external collection, then gives selected evidence to an answerer. This chapter builds a complete local pipeline with a lexical baseline, trained embeddings, an exact vector index, source-labeled context, an extractive answer, and explicit abstention.

Milestone

On a known three-document corpus, you will measure retrieval hit@1, require every answer to carry its source, and reject an unsupported query. You will also identify exactly where a generative language model would enter the pipeline.

1. Begin with a lexical baseline

A retriever ranks documents for a query. Start with something transparent before training embeddings. BM25 rewards shared terms, lets repeated occurrences saturate, gives rare terms more weight, and normalizes for document length. Its outputs are raw ranking scores, not relevance probabilities or calibrated support confidence. For query term t and document d, a common form is:

score(q,d) = Σt∈q IDF(t) · tf(t,d)(k₁+1) / [tf(t,d)+k₁(1−b+b|d|/avgdl)]

Here tf is the term count in d; |d| is document length; avgdl is average collection length; k₁ controls saturation; b controls length normalization; and IDF makes terms found in fewer documents more informative. The reference uses k₁=1.2 and b=0.75, lowercase alphanumeric tokens, and a short stopword list.

One BM25 contribution

Suppose N=10 documents, term t appears in n=2, the candidate contains it once, and its length equals average length. The code uses a positive-smoothed IDF=ln(1+(N−n+0.5)/(n+0.5)), giving ln(4.4)≈1.482. The frequency fraction becomes 1×2.2/(1+1.2)=1, so this term contributes 1.482. A twice-average document gets a larger denominator and a smaller contribution.

BM25 finds “capital France” in the Paris document. It assigns every document zero for “satellites red planet,” because the Mars document says “moons” and “Mars.” The printed top document then comes only from the first-index tie break, not positive evidence. This is a useful failure: exact vocabulary does not express that satellites can mean moons or that Mars is called the red planet.

Lexical retrieval remains valuable for identifiers, names, quoted phrases, and rare strings. A learned retriever is a complement, not proof that term matching can be discarded.

2. Learn embeddings and search them exactly

A dense retriever maps a query and each document to fixed-width vectors, then scores their dot product. Our two-tower teaching model has separate trainable word-embedding tables for queries and documents. One table row is a word embedding. Averaging the rows selected by all words in a document produces that document's embedding; it is not another token embedding. Query embeddings are built the same way from the query-side table. Both tables use contiguous row-major [vocabulary, 8] storage, and every averaged query or document vector has shape [8].

fn dot(left: &[f32], right: &[f32]) -> f32 {
    left.iter().zip(right).map(|(a, b)| a * b).sum()
}

For one supervised pair, raw scores sⱼ=q·dⱼ cover all three documents. The usize target is the index of the known supporting document; it acts as the discrete class label for this ranking objective. Softmax converts these three scores into a training distribution over this declared candidate set, and cross-entropy favors the target. These values are not probabilities that a document is relevant, nor are they support confidence for abstention. If pⱼ is the softmax value and yⱼ is one for the target document, ∂L/∂sⱼ=pⱼ−yⱼ. Therefore ∂L/∂q=Σⱼ(pⱼ−yⱼ)dⱼ and ∂L/∂dⱼ=(pⱼ−yⱼ)q. Those vector gradients are divided among the words that were averaged. The code computes the old query vector and all old document vectors before changing either table, so the document update never reads an already updated query. A central-difference test perturbs one entry on each side and compares the direct cross-entropy slope with the actual training step.

fn cross_entropy_from_logits(logits: &[f32], target: usize) -> f32 {
    let maximum = logits.iter().copied().fold(f32::NEG_INFINITY, f32::max);
    (maximum - logits[target])
        + logits
            .iter()
            .map(|logit| (logit - maximum).exp())
            .sum::<f32>()
            .ln()
}
fn scores(&self, query: &str) -> Vec<f32> {
    let query_vector = self.encode_with(query, &self.query_embeddings);
    self.doc_vectors()
        .iter()
        .map(|document_vector| dot(&query_vector, document_vector))
        .collect()
}

Exact inner-product search

Let normalized query q=(1,0), document vectors d₁=(0.8,0.6) and d₂=(0.6,0.8). Their exact inner products are 0.8 and 0.6, so d₁ ranks first. “Exact” means the index computes every candidate score. It returns the true maximum for these stored vectors rather than an approximate neighbor.

The reference trains six query-document pairs, including “red planet satellites” with target document 0 for the Mars fact and “french seat government” with target document 1 for Paris. train(train_data, steps, learning_rate) cycles through exactly the supplied pairs; one step is one optimizer update, not an epoch. Before subtracting the one-hot target, the normalized vector contains softmax values; afterward the code names it logit_gradients because it contains p−y. The model's loss(data) is mean cross-entropy over whatever labeled pairs the caller supplies. Neither value is a retrieval metric. The default run reports this training loss separately. After training, exact search computes document vectors and linearly scans all three for each query. The run reports three of three hit@1 on different feature combinations such as “two satellites.” Because each query has exactly one relevant document, hit@1 here is also Recall@1. It remains a tiny nearby transfer check.

At millions of documents, scanning every vector can be expensive. Approximate indexes trade recall for search time and memory. This chapter keeps exact search because the corpus is tiny and correctness is inspectable. Training examples determine what paraphrases the embeddings learn; unrelated concepts and new words remain unsupported.

A hybrid retriever can retain both score families. One simple evaluation normalizes BM25 and dense scores on a validation set, adds them with a fixed weight, and ranks the sum. This can recover a rare identifier through lexical matching while using embeddings for surrounding paraphrase. Score scales are not naturally comparable, so adding raw values without calibration is not a principled default. Keep the individual rankings in evaluation to learn which component supplied the winning evidence.

3. Assemble evidence before answering

Retrieval returns identifiers and scores, not a grounded response. Context assembly selects chunks, orders them, fits a context budget, and preserves stable source labels. Our pipeline emits strings such as [france] Paris is the capital city of France.

The answer path is deliberately extractive: each course-authored fact is one sentence, and the answerer returns that exact retrieved sentence. Changing the retrieved text changes the answer without retraining. This proves that external context, rather than a source-ID lookup or separate canonical-answer table, controls the response.

A generative RAG system would place an autoregressive language model after context assembly. Its prompt would contain the source-labeled chunks, query, and an instruction to cite evidence; it would then generate new tokens. Generation can synthesize across passages and paraphrase, but it can also add unsupported claims. The Chapter 36 decoder supplies the mechanism, while a useful grounded generator needs substantially more training than this local fact fixture.

A citation is not proof.

A model can print [france] after a claim that the France passage does not support. Evaluate whether the cited chunk entails the claim, whether all material claims have evidence, and whether the answer is correct. Our extractive baseline has a narrow guarantee because its answer text comes from the selected fact; it cannot synthesize across facts.

This distinction prevents a common naming error. Retrieval plus an extractive reader is a retrieval-augmented answering pipeline, but it is not language-model generation. Retrieval plus a decoder is generative RAG. Both need retrieval evaluation and evidence attribution.

4. Evaluate support and abstain

A system should say “I do not have supported evidence” when the corpus lacks an answer. The project and starter share should_abstain(best, second, known_terms): the query must contain a known content term, the best raw dense score must exceed 0.05, and its margin over the second raw score must exceed 0.02. These thresholds are fixed for the teaching fixture, not probabilities or calibrated confidence.

fn should_abstain(best: f32, second: f32, known_terms: usize) -> bool {
    // ponytail: fixture thresholds do not establish support; calibrate on held-out answerable and unanswerable queries.
    known_terms == 0 || best < 0.05 || best - second < 0.02
}

These gates are heuristics, not a support theorem: “France lunar chess champion” can contain a known term and still ask for a fact absent from the corpus. Extracting a source sentence guarantees where its words came from, not that the sentence answers the question. The unknown-only fixture below tests one narrow rejection path; a broader evaluation must include unsupported queries that overlap supported documents.

The unsupported question “Who won the lunar chess final?” has no useful content term in the index and is rejected. Stopwords such as “the” are excluded from the known-term check; otherwise superficial overlap could turn unsupported text into a confident answer.

Evaluation separates stages. Retrieval hit@1 asks whether the known supporting document ranks first. Answer accuracy compares the returned answer with the known answer. Attribution coverage asks whether an answered item includes the matching source. Unsupported abstention counts whether unanswerable items are rejected. Coverage is the fraction answered; accuracy should be reported at that coverage because rejecting everything trivially avoids wrong answers.

The measured three-query run answers two supported questions, attaches matching source labels to both, and abstains on the one unsupported query. The dense held-out retrieval fixture is 3/3 hit@1. Three examples are executable checks, not a statistically useful benchmark.

A deployed gate needs held-out answerable, unanswerable, and shifted-domain queries. Select thresholds before the final test set, and inspect score calibration. Raw retriever or generator confidence can remain high when the input moves outside training data.
