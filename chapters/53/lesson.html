How can correct weights produce a wrong served prediction?

Training standardizes a raw input x=12 with mean 10 and scale 2, producing 1. If the fitted weight is 2 and bias 1, the prediction is 3. Serving the same weights directly on raw 12 produces 25. The arithmetic works in both programs; their input contracts disagree.

A machine-learning pipeline connects data selection, preprocessing, fitting, evaluation, packaging, and serving. Each stage must preserve the meaning of the next stage’s inputs. Our model artifact therefore stores preprocessing mean and positive scale beside weight and bias. Model::predict owns the transformation (x−mean)/scale so training validation and requests can use the same path.

The tiny training fixture contains five scalar pairs. It fits a standardized affine regressor deterministically. A stored data hash identifies the fixture bytes used by this demonstration; it is an identity aid, not a cryptographic authenticity check. A production artifact would also identify feature definitions, code, dependencies, and evaluation evidence.

Which version number answers which compatibility question?

The text artifact begins with MLMODEL and contains a format version, model version, input-schema version, preprocessing values, weights, and data identity. These are separate concepts. The format says how to decode the bytes; the model version says which release is loaded; the input schema says how a request’s fields should be interpreted.

The decoder checks exact field count, supported versions, finite parameters, and positive preprocessing scale. A file that parses as floating-point numbers can still be unusable: NaN poisons comparisons, infinity can overflow output, and scale zero makes standardization undefined. Reject them at the boundary.

Saving writes a temporary file, synchronizes it, and renames it into place. This avoids readers observing a partially written target under the local filesystem assumptions. It does not provide distributed transactions, authenticated artifacts, or a complete power-loss guarantee for every filesystem. The serving process loads one immutable model before processing requests.

Before sending traffic, compare predictions before and after encode/decode on raw inputs including 8, 10, and 12. Checking weight equality alone could miss changed preprocessing; prediction checks alone on x=mean could miss changed scale. Use probes that exercise each stored field.

What work is allowed before a request becomes a prediction?

The local HTTP endpoint accepts a schema-tagged scalar body such as schema=1&x=12. It bounds header and body reads, validates the route and request framing, parses exactly the supported fields, rejects nonfinite or out-of-range inputs, and returns a JSON prediction. A TCP read may contain only part of a request; reading once and assuming a full message is incorrect.

The optional process is explicit: cargo run --manifest-path labs/s09-advanced/Cargo.toml -- 53 train /tmp/s09-model.txt writes an artifact; cargo run --manifest-path labs/s09-advanced/Cargo.toml -- 53 serve 127.0.0.1:8787 /tmp/s09-model.txt starts the local server until you stop it. Use a fresh path when preserving earlier evidence matters. The server binds only loopback and has per-request read and write timeouts; its process lifetime is intentionally interactive.

Malformed input should produce a client error, while valid input should reach the same model function as the offline probe. The supplied integration test exercises both. This is a sequential teaching server, with no authentication, TLS, concurrent load handling, or remote deployment. Adding those systems would not prove that its predictions are useful.

Monitoring belongs beside validation. Count accepted requests and observe a defined numerical signal only after it passes the boundary. Rejected malformed traffic is a different metric from the distribution of valid model inputs; mixing them makes a shift hard to interpret.

How can a recent change disappear inside a correct average?

Twenty accepted inputs equal 10, followed by four inputs equal 12. The cumulative mean is (200+48)/24≈10.333. A threshold of one unit from baseline 10 does not trigger. The mean of the last four accepted requests is 12 and does trigger. Neither arithmetic is wrong; they answer different time-window questions.

The lab’s target monitor retains a four-request window for drift and a lifetime accepted-request count. On observation, push the new finite value, add it to the window sum, and if the length exceeds four remove the oldest value and subtract it. Mean divides by the current window length, including before the window is full. No observations means no mean.

An input mean shift is evidence of covariate change, not proof of degraded predictive quality. A changed mean can leave accuracy intact; unchanged means can hide changes in variance, subgroups, or the relationship between input and target. Concept drift concerns that relationship and generally requires outcome labels or other evidence unavailable in an immediate request log.

A canary release compares candidate and previous predictions on a declared input set. Here promotion requires every absolute difference to be at most a chosen tolerance. That protects an equivalence-preserving change; it cannot justify an intentionally different and better model without labeled quality criteria. Keeping the previous version enables rollback, but rollback also needs a reason tied to the release’s contract.
