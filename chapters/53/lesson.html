A trained weight vector is not yet a usable ML system. The same preprocessing must reach inference, requests need a contract, artifacts need identities, and operators need evidence for keeping or reversing a release. This chapter turns a tiny linear model into a complete local operational loop.

Operational milestone

The project trains a standardized model, writes a validated versioned artifact with a data fingerprint, serves that artifact through a real local HTTP endpoint, observes input drift, and selects a previous artifact when a candidate fails a canary. It is a miniature for learning contracts, not a production server.

Code and terminology carried forward

Chapter 52 ended with a trained computation and held-out retrieval metrics. This chapter changes the task back to scalar f64 regression so the operational boundary stays visible: one raw input produces one numerical prediction. It keeps the course meanings of weight, bias, learning_rate, predict, and training data. The scalar model now also owns fitted mean and scale, because inference must apply the same normalization as training. The shared naming and shape rules are on the conventions page.

Chapter 11 introduced a checkpoint as validated saved state, and Chapter 38 saved enough optimizer state to resume the exact next update. Chapter 53's MLMODEL artifact instead contains only the state and metadata needed for this model's inference; it makes no exact-resume promise. Its Model::decode parses checkpoint text. That operation is distinct from Chapter 34's tokenizer Bpe::decode, which maps token IDs back to bytes, and from Chapter 36's neural Decoder, which maps token IDs to next-token logits.

1. The model is one stage of a pipeline

Our five training pairs follow y = x−9 for x from 8 through 12. The private train(data, version) function first calculates mean μ = 10 and population variance [(−2)²+(−1)²+0²+1²+2²]/5 = 2, giving scale σ = √2 ≈ 1.414. It then fits ŷ = w((x−μ)/σ)+b. The learned standardized weight approaches √2 and bias approaches one, so raw input 12 produces 3. This compact function fits preprocessing and model parameters together for the teaching fixture. A production pipeline commonly gives the scaler its own fit stage, transforms the training and serving features with that fitted state, and trains the model on the transformed training data; packaging must still bind both fitted objects to the same release.

Inside train, the implementation names its two MSE gradient components and keeps the fixed teaching hyperparameters beside the update:

let mut weight = 0.0;
let mut bias = 0.0;
let learning_rate = 0.05;
for _ in 0..300 {
    let (weight_gradient, bias_gradient) =
        data.iter()
            .fold((0.0, 0.0), |(weight_gradient, bias_gradient), &(x, y)| {
                let normalized = (x - mean) / scale;
                let error = weight * normalized + bias - y;
                (
                    weight_gradient + 2.0 * error * normalized,
                    bias_gradient + 2.0 * error,
                )
            });
    weight -= learning_rate * weight_gradient / data.len() as f64;
    bias -= learning_rate * bias_gradient / data.len() as f64;
}

If serving loads only w and b but forgets μ and σ, it applies a different function. This is training-serving skew. The cure in this project is plain: preprocessing statistics and weights live in one validated model artifact. Neither is allowed to travel alone.

Model::predict reads that stored inference state and retains the fallible boundary used for external inputs:

fn predict(&self, raw: f64) -> Result<f64, &'static str> {
    if self.scale <= 0.0
        || [self.mean, self.scale, self.weight, self.bias]
            .iter()
            .any(|value| !value.is_finite())
    {
        return Err("model parameters are invalid");
    }
    if !raw.is_finite() || !(-1000.0..=1000.0).contains(&raw) {
        return Err("x must be finite and within [-1000,1000]");
    }
    let prediction = self.weight * ((raw - self.mean) / self.scale) + self.bias;
    prediction
        .is_finite()
        .then_some(prediction)
        .ok_or("prediction is nonfinite")
}

A real production pipeline usually has ordered dependencies: ingest data, validate a schema, calculate features, train, evaluate, package, approve, and deploy. Reproducibility requires identifying the inputs and configuration of every stage. The miniature records a deterministic 64-bit fingerprint over the exact training floats. That fingerprint is useful for detecting a changed fixture. It is not a cryptographic authenticity proof and does not replace access control or a signed artifact.

Version three different things separately. The format version tells the loader how bytes are organized. The model version identifies a trained candidate. The input schema version defines the request shape and feature meaning. Increasing a model version does not automatically make an incompatible schema safe, and renaming a file does not migrate either contract.

2. Validate bytes before they become predictions

The artifact is a compact text record:

MLMODEL format model_version input_schema mean scale weight bias data_hash

The loader limits artifact text to 1,024 bytes before decoding. Model::decode requires exactly nine fields including the marker. It accepts only format 1 and schema 1, parses each number, requires a positive scale, and rejects nonfinite parameters. Prediction repeats the model invariant check before using external input. That defense is intentionally redundant at a trust boundary: a malformed in-memory model must not turn into a silent NaN response.

Saving uses a unique temporary file created with “must not already exist,” writes and synchronizes the content, then renames it to the requested path. The final rename prevents readers from observing a half-written artifact on filesystems that provide atomic rename within one filesystem. The temporary file is removed if an earlier step fails. This is a useful local safeguard, though complete crash durability can also require synchronizing the parent directory and understanding the target filesystem.

Why every field participates

Suppose model v1 stores μ=10, σ=2, w=0.75, b=−0.25. For raw x=12, normalized x′=(12−10)/2=1 and ŷ=0.75(1)−0.25=0.5. If serving accidentally uses σ=1, x′=2 and ŷ=1.25. The weight bytes are unchanged, the request is valid, and the answer is still wrong. Checkpoint parity therefore compares the complete inference state, not only learned weights.

Training also validates its data before calculating moments. Finite inputs can still overflow a sum or variance, so μ, σ, and final parameters are checked again. These failures return errors rather than committing a corrupted artifact. Error handling that prevents an invalid model from becoming active is part of the ML algorithm's operational correctness.

3. Put an explicit boundary around inference

The reference uses std::net::TcpListener and implements a deliberately narrow HTTP/1.1 endpoint: POST /predict. The canonical body on the wire is schema=1&x=12.0: the names, version, separator, and scalar value are explicit. It is real serving: a separate client can open a loopback TCP connection, send the request, and receive the loaded model version and prediction.

Small does not excuse ambiguous parsing. The server caps the request line at 256 bytes, each header line at 512, total headers at 2,048, and body at 128. It requires one Content-Length, rejects duplicates, and rejects Transfer-Encoding rather than guessing how two framing schemes interact. parse_body accepts exactly one schema and one x field in either order, rejects duplicates and extras, and bounds finite x to [−1000,1000]. For compatibility with the implemented Rust integer parser, schema spellings such as 01 and +1 also denote supported numeric version 1; emit the canonical schema=1 form. Read and write timeouts prevent one silent local client from holding the server forever.

fn parse_body(body: &str) -> Result<f64, &'static str> {
    let mut schema = None;
    let mut x = None;
    for field in body.split('&') {
        let (name, value) = field.split_once('=').ok_or("fields must use name=value")?;
        match name {
            "schema" if schema.is_none() => {
                schema = Some(
                    value
                        .parse::<u32>()
                        .map_err(|_| "schema must be an integer")?,
                )
            }
            "x" if x.is_none() => x = Some(value.parse::<f64>().map_err(|_| "x must be a number")?),
            "schema" | "x" => return Err("duplicate request field"),
            _ => return Err("unknown request field"),
        }
    }
    if schema != Some(1) {
        return Err("unsupported input schema");
    }
    let value = x.ok_or("missing x")?;
    if !value.is_finite() || !(-1000.0..=1000.0).contains(&value) {
        return Err("x must be finite and within [-1000,1000]");
    }
    Ok(value)
}

HTTP method semantics matter. Prediction is read-only with respect to model state, but POST is not generally idempotent by specification, so clients should not invent retry assumptions from this one handler. A larger system might use a request identifier and a documented retry contract. This project returns 200 only after validation and prediction; malformed input returns a client error response.

Local teaching server ceiling

Requests are handled sequentially. That bounds concurrency and makes shutdown and error behavior easy to inspect, but one slow request delays the next. Add a measured bounded worker pool when concurrent throughput becomes a real requirement. Do not replace it with an unbounded thread per connection.

The server binds to 127.0.0.1 by default, so it is reachable only from the local machine. It has no TLS, authentication, authorization, rate limiting, durable log, or secret handling. Those omissions are explicit limits. Binding it to a public address would change the threat model and requires the missing controls.

4. Observe change, then make rollback concrete

A correct deployment can become wrong when its inputs change. Data drift means the observed input distribution differs from a reference. The project accumulates a count and sum, rejects nonfinite observations and overflow, and compares the live mean with training mean 10. For live values 11.5, 12, 12.5, and 13, the mean is 12.25. With threshold 1.0, |12.25−10| = 2.25 triggers an alert.

The real HTTP loop also observes each successfully validated input, keeps a running count and mean, and prints the mean-drift flag to standard error. Invalid requests do not enter that statistic; restarting the process clears it. This alert does not say accuracy fell. Perhaps a harmless seasonal shift moved x while the same relationship remained valid. Mean alone can also miss variance, tail, categorical, or subgroup changes. Monitoring should connect data statistics with request errors, latency, model outputs, delayed labels, and business outcomes. A threshold is an operational decision calibrated against normal variation and action cost, not a theorem.

Before deployment, the demo creates candidate v2 by deliberately scaling its weight. Canary inputs 8, 10, and 12 are scored by candidate and previous model. If any absolute difference exceeds 0.25, rollback selects v1. The measured default run prints canary rollback selected previous version: true.

The selection becomes an artifact choice. The service loads that chosen artifact at startup. This is not a live atomic model swap inside a fleet: an operator must point the process at the previous file, restart or reload it, and verify health. Database migrations or feature changes may also need reversal. A rollback plan is credible only when the old dependencies remain available and compatibility has been tested.

The response body includes version=1 prediction=3.000000. The ordinary test suite checks artifact and parser logic without sockets. A loopback integration test is marked ignored because some sandboxes forbid binding; on a host that permits local sockets, run cargo test --manifest-path projects/ch53/Cargo.toml -- --ignored.

With mean 10, scale 2, weight 0.75, and bias −0.25, its supplied validation confirms that raw input 12 predicts 0.5. The tiny ch53_01.rs exercise deliberately isolates the canonical serialized field: unlike the full parser, its literal match accepts only schema=1 and rejects alternate spellings. The solved operation is:

fn parse_schema(field: &str) -> Result<u32, &'static str> {
    match field {
        "schema=1" => Ok(1),
        _ => Err("unsupported schema"),
    }
}

Practice

  1. Accept exactly one supported integer schema field and one finite x field in the starter; reject missing, duplicate, or extra fields, and emit schema=1&x=<scalar> as the canonical form.
  2. Debug a deployment that passes weight parity but changes every prediction. Compare mean, scale, input schema, and feature order.
  3. Debug clients that sometimes hang. Check request-size caps, read timeouts, and whether the declared content length matches bytes sent.
  4. Independent variation: add a two-window variance statistic and an output-prediction mean. Define separate thresholds and print which one caused the alert.
Hint 1: validation order

Validate structure first, parse types second, check supported schema and numeric bounds third, then call the model.

Hint 2: rollback

Keep v1 immutable. Let canary evaluation return the artifact to load; do not overwrite the last known good file with candidate bytes.

Worked answer

Split the starter body on &, split fields once on =, fill one optional schema and x slot, reject a second assignment or unknown name, require schema one, then require finite x. A preprocessing mismatch explains global prediction movement despite equal weights. For the variance extension, record count, sum, and sum of squares with finite checks and label every reference window.
