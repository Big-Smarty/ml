Reference interfaces and shapes

Chapter 35 introduced causal attention with direct f64 Q, K, and V arrays shaped [positions,width] for one head. It returned a complete [positions,positions] probability matrix so the backward pass could reuse it. Chapter 36 moved to f32, projected Q/K/V inside a decoder, and used several equal-count heads. This standalone chapter keeps direct Q/K/V inputs and forward attention only, but changes their layout to grouped-query attention: queries are [positions,query_heads,head_width], keys and values are [positions,kv_heads,head_width], and output has the query shape. Arrays are flat, contiguous, and row-major by position, then head, then lane.

The inputs are already-projected vectors. They are neither token IDs nor learned projection weights. A query_position identifies a row in the sequence; a token ID would identify a vocabulary entry before projection. Query-key dot products produce attention scores. Stable softmax converts the permitted scores into normalized attention probabilities, sometimes called attention weights; those data-dependent probabilities are distinct from learned model weights. The project has no learned parameters, loss, gradient, optimizer step, or training loop. Chapter 40 uses token IDs and learned weights in a decoder and stores projected K/V vectors across inference positions; Chapter 42 isolates the attention arithmetic and GQA head mapping. The shared names and shapes follow the course conventions.

What output must every implementation preserve?

For query Q, key K, and value V, scaled dot-product attention is softmax(QKᵀ/√d)V. Here d is head_width, the number of lanes in one head. Division by √d keeps dot-product magnitudes from growing unchecked as a head gets wider. The causal mask permits key position j only when j ≤ query position i.

Let T count sequence positions, Hq query heads, and Hkv K/V heads. Q has shape [T,Hq,d], K and V have shape [T,Hkv,d], and output has Q’s shape. The flat offset for (position, head, lane) is (position * heads + head) * head_width + lane. Each query head computes its own score row and probability distribution even when another query head shares the same K/V head.

The reference names its two implementations by role. causal_attention_scalar is the clear oracle: for one query position and one query head, it creates only the permitted score row, finds its maximum, computes the shifted denominator, and immediately uses the normalized probabilities to combine values. It then discards that row before processing the next query/head. “Scalar oracle” describes this simple loop and its one-row workspace; it does not imply an allocation of all HqT² scores or probabilities.

Stable softmax by hand

For attention scores [1,3,2], subtract maximum 3 to obtain [−2,0,−1]. The shifted exponential masses are about [0.1353,1,0.3679], with denominator 1.5032. Dividing by that denominator gives probabilities [0.0900,0.6652,0.2447]. The masses are not yet probabilities, and neither quantity is a learned model weight. Subtracting one common maximum leaves the normalized probability ratios unchanged while avoiding a large positive exponential.

Inside the supplied per-head scalar oracle, these two lines establish the shared exponential reference before each mass is normalized:

let maximum = scores.iter().copied().fold(f32::NEG_INFINITY, f32::max);
let denominator: f32 = scores.iter().map(|score| (*score - maximum).exp()).sum();

The oracle makes floating-point order easy to inspect. Tiling changes that order, so bitwise equality is not expected. The test bounds each absolute error by 2×10⁻⁶ + 2×10⁻⁶|reference|, a mixed tolerance selected for the small f32 fixtures. Longer reductions need their own error study. Another test fixes the causal and GQA mapping together: at the first position, each query head’s output equals the only visible value from its assigned K/V head.

What must be rescaled when a new maximum arrives?

Online softmax keeps a running maximum m and a shifted denominator ℓ. When a new score x arrives, compute m′ = max(m,x) and ℓ′ = ℓ exp(m−m′) + exp(x−m′). Start with m = −∞ and ℓ = 0. In the code these quantities are running_maximum and shifted_denominator. Together they are softmax state, not normalized probabilities and not an optimizer state.

Trace the recurrence

Process [1,3,2]. After 1, m=1 and ℓ=1. When 3 becomes the new maximum, rescale the previous unit by exp(1−3)=0.1353 and add one, giving ℓ=1.1353. Score 2 does not change the maximum; add exp(−1)=0.3679, giving ℓ=1.5032. This is the same shifted denominator used by the ordinary two-pass softmax above. Only after dividing each shifted mass by ℓ do we obtain probabilities.

Attention needs a value-weighted numerator as well as the denominator. causal_attention_tiled keeps shifted_value_numerator, a vector with head_width lanes. When the maximum rises, it multiplies every old lane and the old denominator by exp(m−m′). For each new score xⱼ and value vⱼ, it adds exp(xⱼ−m′)vⱼ to that numerator and exp(xⱼ−m′) to the denominator. After every visible key position has been processed, dividing the vector by ℓ produces the attention output. Individual normalized probabilities need not be stored.

Rescaling preserves the shared exponential reference. Updating the maximum while leaving older numerator and denominator terms on their previous scale combines incomparable numbers. The mistake can pass a decreasing-score example because its maximum never changes. The fixed lab and reference fixtures use an increasing score, so the rescaling branch must work.

How can separate key tiles share one normalization?

A key tile is a bounded block of key positions and their values. For each query position and query head, causal_attention_tiled visits permitted key positions in blocks of key_tile_width. It computes the tile’s score vector and maximum, merges them into the running softmax state, rescales the accumulated value numerator, then advances. The running state persists across every tile in that query row.

No approximation is introduced: both implementations evaluate every pair allowed by the causal mask, use the same GQA head mapping, and normalize over all keys from position zero through the current query position. “Exact” means the same dense attention formula within floating-point reordering error. The arithmetic remains O(HqT²d). Sparse or windowed attention removes pairs and is a different algorithm.

next_maximum = max(running_maximum, tile_maximum)
old_scale = exp(running_maximum - next_maximum)
shifted_value_numerator *= old_scale
shifted_denominator *= old_scale
for score, value in key_tile:
    shifted_mass = exp(score - next_maximum)
    shifted_value_numerator += shifted_mass * value
    shifted_denominator += shifted_mass

FlashAttention applies this identity with hardware-aware query and key blocks so intermediate score data can remain in faster memory. This chapter’s ordinary CPU vectors demonstrate the recurrence and bounded tile workspace. They do not reproduce a GPU kernel, its on-chip schedule, a fused backward pass, or its performance.

A hypothetical fully materialized f32 score tensor for T positions and Hq query heads needs 4HqT² bytes before any separate probability or backward storage. Doubling T multiplies that square allocation and the dense pair count by roughly four. The scalar oracle in this project already avoids the square allocation by holding one O(T) causal row. The tiled implementation reduces that row workspace further to at most B scores plus d numerator lanes. The caller retains the full Q/K/V inputs, whose element counts are THqd for Q and THkvd for each of K and V; each attention path allocates its own THqd output and temporary workspace.

For Hq=8 and T=4,096, a square score tensor would contain 8×4,096² f32 values: 536,870,912 bytes, about 512 MiB. At T=8,192 it would be about 2 GiB. These are arithmetic estimates for that one hypothetical tensor, not measured resident memory for this program. Causal masking leaves roughly half its entries useful, but an implementation that allocates a square tensor still reserves every cell. Training could also retain probabilities and other activation state for backward; Chapter 42 implements forward only.

Key-tile width B controls this implementation’s temporary score vector. B=1 stores one score; a very large B approaches the scalar oracle’s row workspace. It also changes allocation and loop behavior, so no tile width is declared fastest. Hardware kernels choose both query and key block shapes from registers, shared memory, alignment, and occupancy. This CPU benchmark measures only the two allocating functions as written.

Which query heads share keys and values?

Standard multi-head attention has one key head and one value head for every query head. Grouped-query attention, or GQA, uses fewer K/V heads. When Hq is divisible by Hkv, contiguous groups of Hq/Hkv query heads read one K/V head. Both the scalar oracle and tiled recurrence compute kv_head = query_head / (query_heads / kv_heads) before scoring, so their reference comparison checks the same group mapping.

Map four query heads to two K/V heads

Let Hq=4 and Hkv=2. The group size is two. Query heads 0 and 1 use K/V head 0; query heads 2 and 3 use K/V head 1. At query position zero, the causal mask permits only key position zero. The test therefore expects the first two query-head outputs to equal value head 0 and the next two to equal value head 1. This single fixture catches a reversed grouping or an incorrect mask boundary.

When Hkv=Hq, the mapping becomes ordinary multi-head attention. When Hkv=1, every query head shares one key and value head, usually called multi-query attention. The validation rejects zero dimensions, mismatched flat lengths, nonfinite inputs, and any Hq not divisible by Hkv.

In a complete trained decoder, fewer K/V heads can reduce K/V projection parameters and per-position cache storage. This project contains neither projections nor a decoder cache; it receives K and V directly. Its own concrete storage reduction is that those input arrays have THkvd elements instead of THqd. GQA does not remove any query-position/key-position comparisons, and random fixtures do not measure model quality.
