Give each machine group a validation turn

Divide development machines into three fixed blocks:0–5,6–11,12–17. Fold 0 validates later rows from the first block and trains earlier rows from the other two. Fold 1 rotates the second block into validation; fold 2 rotates the third. Every eligible days 5–7 row receives one validation prediction. Earlier rows are training candidates, and gap rows are intentionally excluded from cross-validation.

This is group-and-time-respecting cross-validation. It is not ordinary random k-fold over all 144 rows. Random stratification balances labels but cannot prevent a machine's future data from teaching a predictor evaluated on its past. A small label imbalance within a legal fold is preferable to violating the deployment question.

Implement folds by filtering raw rows for each held block, then sort both sides by stable row ID. Sorting matters because nearest-neighbor ties and incremental algorithms can depend on traversal. Do not fit a scaler before building the folds.

Search the declared budget without moving the goalposts

A model parameter is estimated by its fitting rule; a hyperparameter controls that rule from outside, such as k, a variance floor or maximum tree depth. This exercise has six declared candidates, two per family. That equal count makes the opportunity budget visible, although it does not make compute costs or model complexity equal.

For three equally sized validation folds with costs[.5,1,.75], pooled cost is.75. With unequal fold sizes, averaging their percentages can be wrong: one error in 2 cases and one in 8 cases is 2/10=.2 error overall, not(.5+.125)/2=.3125. The supplied trial pools all prediction/outcome pairs before computing metrics.

Implement search: visit every supplied candidate in order, call trial, store its full predictions and per-fold costs, and update the winner only when cost is strictly lower. Return an index into the complete trial vector. Reject an empty candidate set. Compare the frozen cost, not accuracy or Brier opportunistically.

Grid search visits a declared list. Random search samples a declared distribution and seed within a fixed budget; it can cover useful dimensions more efficiently when only some settings matter. This lab uses a tiny explicit grid for inspectability. Neither method prevents validation overfitting when enough alternatives are tried.

Hint: use strict improvement

Initialize the winner to the first computed trial. A later equal score must keep the earlier winner. Deterministic tie-breaking is part of the protocol, not an afterthought chosen because one model sounds more appealing.

The prevalence rule emits that training frequency as every probability. They can have identical decisions but different Brier scores. Preserved miniature reference

The earlier standalone reference remains intact. This source-tagged excerpt illustrates the same operation on its original miniature fixture; its types and results are separate from the shared maintenance lab.

fn probability(&self, features: [f64; 2]) -> f64 {
    let features = self.scaler.transform(features);
    sigmoid(self.weights[0] * features[0] + self.weights[1] * features[1] + self.bias)
}
fn predict(&self, features: [f64; 2]) -> u8 {
    u8::from(self.probability(features) >= 0.5)
}

Turn mistakes into testable next-cycle hypotheses

Error analysis inspects individual mistakes and defined subsets of cases after computing the aggregate metric. It turns an unexplained score into specific hypotheses for a later development cycle.

The report prints each error's stable ID, machine, day, regime, missing-temperature flag, probability, label and signed probability residual p−y. A large positive residual is an overconfident false alarm; a large negative residual is a missed failure. For predicted.2 and observed 1, residual is−.8 and its Brier contribution is.64.

It also reports observed-temperature, missing-temperature and unseen-turbo slices with denominators. The selected tree gets all five missing-temperature final rows wrong on this fixture.
