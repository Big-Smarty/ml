If preprocessing sees validation rows, repeated tuning adapts to one test set, or a sophisticated model gets more chances than its baseline, the final percentage is biased. This capstone turns the course's evaluation lessons into one reproducible experiment.

Chapter 4 introduced LogisticModel with step and train updates on an existing model. Here LogisticModel::fit(train_data, config) starts from zero parameters, fits fold-only scaling, runs the configured updates, and packages the scaler with the learned weights and bias. Consequently probability and predict receive raw features and transform them with the stored training statistics before inference.

fn probability(&self, features: [f64; 2]) -> f64 {
    let features = self.scaler.transform(features);
    sigmoid(self.weights[0] * features[0] + self.weights[1] * features[1] + self.bias)
}
fn predict(&self, features: [f64; 2]) -> u8 {
    u8::from(self.probability(features) >= 0.5)
}

The logistic update uses error = probability - label, retaining the course's prediction-first signed-error convention. Chapter 15's boosting residual was target - prediction = -error because the next stump learned a regression correction; that reversed residual is not used here.

The fitter's implicit objective is mean binary cross-entropy over the training-fold rows plus 0.5 * l2 * (weights[0]² + weights[1]²). Accordingly, data gradients are divided by the training row count, l2 * weight is added to each weight gradient, and the bias is not regularized. The chapter evaluates fitted classifiers with accuracy rather than presenting cross-entropy as the held-out metric.

1. Write the evaluation contract before tuning

Start by defining the prediction unit, target, split unit, and primary metric. A row is not always an independent unit. Several rows may come from one patient, device, household, or future time period. If related rows cross between training and validation, a model can recognize their shared signature rather than learn a transferable relationship.

The bundled fixture treats rows as independent and uses binary accuracy. It has 24 development rows with IDs 1–24 and eight separate test rows with IDs 101–108. The program never places test rows in cross-validation, scaling, or hyperparameter selection. Stable IDs make membership auditable even if array order changes.

An evaluation protocol records the frozen data snapshot, target, split rule, metric, candidate list, seed, and stopping rule. Reproducibility means another run can reconstruct the same experiment from those choices. A seed alone is insufficient if row ordering, preprocessing, or candidate order can drift.

Count the information available to each stage

With 24 development rows and four folds, each fold validates on six rows and trains on eighteen. Four candidates require 4×4 = 16 fitted fold models. After selection, one model is fitted on all 24 development rows. The eight test rows are scored once. That is 17 fits, with no test row affecting any fitted parameter.

Time and groups change the split rule. Forecasting needs past-to-future validation. Repeated subjects need group-held-out folds. Stratification, used here, preserves class proportions; it does not repair dependence among rows. Choose the split that resembles how new data will arrive.

2. Cross-validation reuses development data safely

In k-fold cross-validation, every development row belongs to exactly one validation fold. For each fold, fit on all other folds and score on the held-out one. Each row contributes once to validation and k−1 times to training across separate fits.

The reference sorts row indices by label and a deterministic integer mix of row ID with seed 20260908. It then distributes each class round-robin across four folds. Each fold receives three zeros and three ones. Integer mixing avoids clock time and external randomness, and sorting fixes the traversal order.

Aggregate unequal folds correctly

Suppose one validation fold has 8 correct of 10 and another has 1 correct of 2. Their unweighted mean accuracy is (0.8+0.5)/2 = 0.65. But each validation row should have equal influence, so pooled accuracy is (8+1)/(10+2) = 9/12 = 0.75. Equal-size folds make the two calculations coincide; robust code should state which reduction it uses.

Report individual fold scores or their spread when they reveal instability. Fold scores are correlated because their training sets overlap, so their standard deviation is not automatically a confidence interval. Cross-validation estimates a procedure under its split assumptions; it does not make a small or biased dataset representative.

The test for stratified_folds checks determinism, valid fold IDs, and exactly three examples of each class in every fold. These are stronger invariants than asserting one final accuracy. If a row is duplicated or omitted, an attractive mean score cannot rescue the evaluation.

3. Fit every learned transformation inside the fold

Logistic regression benefits from feature scaling. For each training fold, the project computes its feature means and standard deviations, stores them with the model, and transforms that fold's validation rows. The validation rows never influence those statistics. Following Chapter 14, a constant training-fold feature receives scale one and therefore transforms to zero after centering. Chapter 3 rejected zero variance in its standalone scaling exercise; this later policy keeps a valid cross-validation fold trainable when one feature happens to be constant.

fn transform(&self, features: [f64; 2]) -> [f64; 2] {
    [
        (features[0] - self.mean[0]) / self.scale[0],
        (features[1] - self.mean[1]) / self.scale[1],
    ]
}

Computing the scaler once on all 24 development rows before cross-validation is data leakage. No labels need to leak. A validation-only outlier can change the global mean and scale, telling the training process something about held-out feature distribution. Imputation, category vocabularies, PCA, feature selection, and anomaly thresholds follow the same training-only rule.

let train_data = rows where fold != held_out;
let validation_data = rows where fold == held_out;
let model = LogisticModel::fit(&train_data, config)?; // scaler fitted here

After the configuration is selected, refitting the scaler and model on all development rows is legitimate. Selection is finished, so all development data can support the final parameters. The untouched test set then estimates this frozen procedure. Its scaler still comes only from development rows.

Do not peek and rename.

If the test score causes you to change features, candidates, thresholds, or seed, the test has become development data. Record that honestly and obtain a new untouched test set for a final estimate.

4. Search a fixed budget and compare fairly

A hyperparameter controls training but is not learned by the model's gradient. The reference candidates vary learning rate, L2 strength, and epoch count. Every candidate uses the same folds, metric, and preprocessing code. The list is fixed at four before scores are observed.

A grid with four parameters and five values each contains 5⁴ = 625 candidates. Five-fold validation would require 3,125 fits. Bigger searches are not automatically fairer: by trying more alternatives, a model family gets more chances to fit quirks in validation folds. Random search can cover large spaces more efficiently when only some dimensions matter, but its distribution and seed must also be frozen.

The reference breaks score ties by retaining the earliest candidate. This makes results stable and rewards the predetermined order rather than accidental sorting. All four candidates happen to score 100% on the simple development fixture. The first is therefore chosen. That tie is a lesson, not proof that hyperparameters never matter. The selected Config remains a record of chosen settings; refitting converts those settings and all development rows into new stored weights, bias, and scaler statistics.

The baseline predicts the majority development label for every test row. It receives the same frozen development/test boundary and accuracy metric. Logistic regression then answers a concrete question: does a learned linear relationship beat the no-feature baseline? On a balanced test set, the majority baseline scores 50%; the fitted LogisticModel scores 100%.

This is a fair comparison between one trivial baseline and one learned model. It is not a tournament among every algorithm from Chapters 14–18. Comparing k-nearest neighbors, a tree, and an SVM would require bringing each implementation under the same fold builder, training-only preprocessing, candidate budget, and metric. Add that only when the scientific question calls for model-family comparison.

For an unbiased estimate after extensive search, nested cross-validation adds an outer loop. Each outer training portion runs its own inner search, and the outer held-out portion evaluates the complete selection procedure. Three outer folds, four inner folds, and six configurations require 3×4×6 = 72 inner fits plus three outer refits. This is valuable when data is scarce, but the fixed development/test capstone is simpler and auditable.

5. Finish with error analysis, not one score

Accuracy compresses every prediction into one number. Error analysis returns to individual rows and asks where the system fails. The reference prints stable IDs for every misclassified test row. Its clean fixture prints an empty list, so a useful variation should add ambiguous or mislabeled rows.

Group errors by meaningful, pre-existing slices such as device type, acquisition period, or missingness pattern. Record both errors and denominators: two mistakes among three examples differ from two among three thousand. Avoid inventing slices after seeing one surprising row and presenting them as confirmatory evidence.

Inspect high-confidence mistakes first for label problems, leakage, unit errors, and population shifts. Then compare false positives and false negatives because equal accuracy can hide different costs. Error analysis may motivate a new feature or model, but that begins a new development cycle. It does not change the frozen test result already observed.

A compact experiment record should include row IDs or a dataset checksum, fold assignments, seed, candidate configurations in order, per-candidate fold results, selected configuration, final test metric, and error IDs. The project prints enough to inspect the mechanism. A production capstone would save this manifest alongside code and model artifacts.

Worked solution
fn pooled_accuracy(fold_counts: &[(usize, usize)]) -> f64 {
    let correct: usize = fold_counts.iter().map(|&(correct, _)| correct).sum();
    let total: usize = fold_counts.iter().map(|&(_, total)| total).sum();
    correct as f64 / total as f64
}

For (8,10) and (1,2), this returns 9/12 = 0.75. Averaging 0.8 and 0.5 would incorrectly give each fold equal weight instead of each held-out row.

Debugging · Validation improves after a global scale

A learner fits the scaler on all development rows before generating folds. One validation row has an extreme feature value.

Answer

The extreme validation value changed the transform used for training, so information crossed the split. Build raw training and validation rows first; fit the scaler on train_data; call transform with its stored statistics on validation features. Add a regression test in which changing only a validation feature cannot change the fitted training scaler.

A zero standard deviation uses scale one, leaving a constant centered feature at zero. A small but nonzero standard deviation is still used: comparing it with machine epsilon would make scaling depend incorrectly on the units of measurement.
