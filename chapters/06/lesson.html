A correct gradient does not choose its own step size, batch, or stopping point. Training can crawl, oscillate, diverge, or fit noise while every derivative is right. Reliable optimization means measuring these behaviors on training and held-out data and understanding which control changes which failure.

Your goal

You will compare deterministic learning curves for small and useful learning rates, diagnose unstable rates with worked arithmetic, update from minibatches, add L2 regularization, and distinguish fitting the training set from improving validation performance.

Code and terminology carried forward

Chapter 2 trained the scalar Neuron { weight, bias } by calling predict(&self, input), loss(&self, data), gradient(&self, data), step, and train. Chapter 5 then separated data used for development from held-out evaluation. This chapter combines those ideas. The model, prediction, signed error = prediction - target, and ordinary mean squared loss keep their earlier meanings. The course conventions give the shared interface.

Three additions are justified by the new comparison. step now receives one batch plus l2, the strength of the L2 penalty. train receives explicit train_data and validation_data, an epochs count, batch_size, learning_rate, and l2. One optimizer step updates the neuron from one batch; one epoch is a complete pass through train_data and can contain several steps. The code never hides either dataset inside loss or train.

#[derive(Clone, Copy, Debug)]
struct Neuron {
    weight: f64,
    bias: f64,
}
fn predict(&self, input: f64) -> f64 {
    self.weight * input + self.bias
}

1. Optimization has its own failure modes

Our project fits noisy points near y = 2x+1. Noise means the targets do not land exactly on one line. The training set determines updates; a separate validation set asks whether those updates transfer to points not used in gradients.

A learning curve records a metric across epochs. Here an epoch means one pass through all 12 training examples. At each epoch boundary, the project calls model.loss(train_data) and model.loss(validation_data). Both are ordinary MSE averaged over every example in the supplied slice, without the regularization penalty, so their vertical values are directly comparable.

fn loss(&self, data: &[(f64, f64)]) -> Result<f64, &'static str> {
    if data.is_empty() {
        return Err("loss requires at least one example");
    }
    if !self.weight.is_finite()
        || !self.bias.is_finite()
        || data
            .iter()
            .any(|(input, target)| !input.is_finite() || !target.is_finite())
    {
        return Err("model and examples must contain finite numbers");
    }
    let loss = data
        .iter()
        .map(|&(input, target)| (self.predict(input) - target).powi(2))
        .sum::<f64>()
        / data.len() as f64;
    if !loss.is_finite() {
        return Err("loss overflowed; reduce input scale or learning rate");
    }
    Ok(loss)
}

Read three curve patterns

If training and validation loss both fall slowly, the learning rate may be too small. If both jump upward or become nonfinite, updates are unstable. If training loss keeps falling while validation loss reaches a minimum and rises, the model is fitting training-specific variation. These patterns are diagnostic clues, not unique proofs: poor features or an inadequate model can also keep both losses high.

One final number hides the path. A model ending at validation MSE 0.3 after smooth improvement differs operationally from one that hit 0.05, diverged, and later returned by chance. Curves reveal when a checkpoint was best and whether a claimed final setting is stable.

2. The learning rate scales a local direction

Gradient descent uses θnew = θ−ηg. The gradient g supplies a local direction; learning rate η chooses distance. In Rust, η is the learning_rate argument. Multiplying it by ten multiplies the immediate parameter change by ten. It does not simply make the same path ten times faster because the next gradient is evaluated at a different point.

Overshoot on a one-parameter bowl

Let L(w) = (w−2)², whose derivative is 2(w−2). Starting at w = 0 gives gradient −4. With η = 0.1, w becomes 0.4 and loss falls from 4 to 2.56. With η = 1.1, w becomes 4.4 and loss rises to 5.76: the direction was correct, but the step crossed the minimum too far.

At η = 1, the sequence alternates exactly between 0 and 4 and never improves. At η = 0.01, it moves to 0.04 and improves safely but slowly. Curvature and feature scale determine which rates work.

The reference compares learning_rate 0.001 with 0.03 while keeping other choices fixed. The worked example diagnoses an unstable 1.1 step rather than running a deliberately divergent default. This is a controlled comparison, not a universal recommendation. Learning rates depend on loss reduction, batch size, scaling, model, and optimizer. Reject nonpositive or nonfinite learning rates at the boundary; silently accepting NaN makes every later measurement meaningless.

3. Minibatches trade exactness for frequent updates

A full-batch update averages all N examples. A minibatch uses B examples, with 1 ≤ B ≤ N. Its MSE gradient is an estimate of the full gradient. Smaller batches make more updates per epoch and each update costs less, but batch-to-batch variation makes the path noisier.

Two batches disagree without either being wrong

At w = b = 0, consider points (−1,−1) and (1,3). The first weight-gradient contribution is 2(1)(−1) = −2. The second is 2(−3)(1) = −6. A batch containing only the first estimates −2; one containing only the second estimates −6; the two-example full gradient averages to −4. Each single-example gradient is correct for its batch.

The project uses train_data.chunks(batch_size). With 12 examples and batch_size = 4, each epoch contains three batches and therefore three optimizer steps. An 80-epoch run makes 240 updates. Changing the batch size to 12 gives one step per epoch and only 80 updates, so equal epoch counts do not mean equal step counts. Fixed ordered batches make this demonstration deterministic and easy to trace. This is a deliberate teaching simplification. In ordinary stochastic training, shuffle training examples between epochs so a fixed order does not repeatedly pair updates with trends or class blocks. A production run should record its seed and shuffle algorithm.

Gradient reduction is averaged within each batch. The last batch can be shorter and must divide by its own length. Accumulating gradients across several minibatches before updating can simulate a larger batch, but only if the reduction factors are handled consistently. We do not add that mechanism here.

4. Favor a smaller weight when fits are similar

Optimization minimizes the objective supplied to it. If a flexible model can reduce training error by following noise, a smaller training loss may accompany worse validation loss. Regularization modifies training to prefer some solutions over others.

The project adds an L2 penalty λw² to each minibatch training objective. The Rust argument l2 is λ and must be nonnegative. The derivative is 2λw, so the weight update uses data_gradient.weight + 2.0 * l2 * self.weight. This term has the sign of w, and subtracting it pulls weight toward zero. The bias is not penalized because shrinking a constant offset usually does not control sensitivity to input; this convention must be stated.

loss(data) deliberately remains the unregularized data MSE established earlier. During a step, the optimized objective is loss(batch) + l2 * weight². Training and validation curves report only loss, so the two splits stay comparable even when the training update includes L2. Calling the combined quantity generic loss would hide which data and penalty produced it.

Combine data and penalty gradients

Suppose the data gradient for w is −3, current w = 2, and λ = 0.1. The penalty gradient is 2(0.1)(2) = 0.4. Total gradient is −2.6. At learning_rate = 0.05, w increases by 0.13 rather than the unregularized 0.15. Data still asks for a larger weight, but regularization resists it.

If w = −2, the penalty contribution is −0.4, which pushes an update toward zero from the other side. L2 is smooth and symmetric.

The implementation keeps the Chapter 2 data gradient intact, then adds only the new penalty component before the simultaneous update:

fn step(self, batch: &[(f64, f64)], learning_rate: f64, l2: f64) -> Result<Self, &'static str> {
    if !learning_rate.is_finite() || learning_rate <= 0.0 {
        return Err("learning rate must be finite and positive");
    }
    if !l2.is_finite() || l2 < 0.0 {
        return Err("L2 strength must be finite and nonnegative");
    }
    let data_gradient = self.gradient(batch)?;
    let gradient = Gradient {
        weight: data_gradient.weight + 2.0 * l2 * self.weight,
        bias: data_gradient.bias,
    };
    let next = Self {
        weight: self.weight - learning_rate * gradient.weight,
        bias: self.bias - learning_rate * gradient.bias,
    };
    next.loss(batch)?;
    Ok(next)
}

Regularization can improve generalization, performance on new examples from the intended distribution, but it is not automatically beneficial. Too much λ underfits a real signal. Choose it with validation data, then report final test behavior. The reference includes λ = 0.1 as a visible comparison, not an optimum claim.

Model capacity, more representative data, early stopping, augmentation, and other methods can also affect generalization. L2 is one concrete tool whose arithmetic fits this chapter. It cannot repair leakage or a train/production distribution mismatch.

5. Run and inspect the comparison

Read the complete reference. step computes the mean data gradient from its explicit batch and adds the L2 term only to the weight. train receives both data slices explicitly, calls one step per batch, and records both curves before training and after every epoch. TRAIN and VALIDATION are fixed course-authored noisy-regression fixtures supplied by main; the methods do not capture them.

cargo run --release --manifest-path projects/ch06/Cargo.toml

The demonstration reports start and end train/validation MSE plus learned parameters for slow, steady, and L2 runs. Tests require the steady run's validation MSE below 0.2, its weight within 0.15 of two, and the regularized weight smaller in magnitude than the unregularized weight. These are fixture-specific checks, not general thresholds.

Perform three controlled experiments. First change only learning_rate from 0.03 to 0.003 and compare early curve values. Second change only batch_size from four to twelve; there will be one full-batch step per epoch rather than three minibatch steps, so equal epoch counts do not mean equal update counts. Third increase l2 to 1 and watch training and validation errors. Predict each direction before running.

Nonfinite updates return an error rather than being printed as a curve. This is failure detection, not recovery. Real training may lower the learning rate, restore a known-good checkpoint, and record diagnostics, but silently continuing from infinity or NaN destroys the run.

Validation is used for choices, not final proof.

Once you compare rates and λ using validation, validation performance is optimistic for the selected configuration. Preserve a separate test set for the final estimate, as Chapter 5 established.

Debugging · The last batch is underweighted

Ten examples use batch size four. A learner divides every batch gradient by four, including the final two-example batch. What changes?

Answer

The final batch's summed contributions are divided by four instead of two, halving that update relative to other batch means. Divide by batch.len(). If you intend a dataset-level weighted accumulation, define and implement that different reduction explicitly.

Independent variation · Early stopping

Modify a local copy to remember the model with the lowest validation MSE. Stop after validation has failed to improve for five epochs. What state must be saved?

Worked answer

Store the best validation loss, a copy of the corresponding model, and the number of epochs since improvement. Reset the counter on improvement; otherwise increment it. Return the saved best model, not the final worse model. A real resumable run must also save optimizer and data-order state.
