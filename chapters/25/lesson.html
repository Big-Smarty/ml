The recommender from Chapter 24 can spend most of its time multiplying the same kinds of rows and weights used throughout this course. “Make it faster” sounds concrete, but it is not yet a testable claim. This chapter turns performance into an experiment: preserve a correct scalar answer, isolate one dense-inference kernel, measure repeated release builds, and report both latency and useful work.

1. The same formula can produce nearby answers

Chapter 9 defined dense inference as Y=XWT+bias with the shapes listed above. That mathematical formula uses real numbers. A computer stores a finite set of floating-point numbers. An f32 value has 24 bits of significand precision when the implicit leading bit is counted, so most real results are rounded to a nearby representable value.

Rounding makes addition order observable. In exact arithmetic, (a+b)+c equals a+(b+c). With f32, let a=100,000,000, b=−100,000,000, and c=1. The first grouping produces 0+1=1. The second tries to represent −99,999,999, rounds it near −100,000,000, and then produces 0. An optimizer that groups partial sums differently can be correct while changing low bits.

A fused multiply-add computes a*b+c with one final rounding, rather than rounding the product and then the sum. That can improve accuracy and change the result relative to separate operations. The hardware may also use wider vector lanes. Therefore an optimized f32 kernel should agree with a scalar or f64 reference within an absolute-plus-relative tolerance; bitwise identity is the wrong universal contract.

Count one dense output

For one input row [1,2,3], one weight row [0.5,−1,0.25], and bias=0.1, the output is 0.1+1×0.5+2×(−1)+3×0.25=−0.65. There are three multiplications and three additions when adding into the bias. Performance work conventionally counts the multiply-add body as 2×in_features=6 floating-point operations, or FLOPs. That operation count describes the algorithm; it is not a measurement of instructions or time.

The project keeps the timed inputs, weights, bias, and outputs as f32, matching common inference storage, but recomputes the deterministic fixture with f64 accumulation before timing. This numerical oracle does not prove the formula is correct by itself; the small hand calculation and shape tests do that. It catches later changes that corrupt or omit outputs.

2. Measure a question, not a whole afternoon

A benchmark is a controlled measurement of a named workload. The question here is: how long does one already-allocated dense forward pass take for fixed dimensions and values? Constructing inputs, allocating outputs, printing, and correctness checking happen outside the timed interval. End-to-end request latency is also useful, but it answers a different question and should be reported separately.

The kernel below is the complete timed operation. Its public argument order follows the logical data flow from inputs and parameters through dimensions to the output buffer.

fn dense(
    inputs: &[f32],
    weights: &[f32],
    bias: &[f32],
    batch: usize,
    in_features: usize,
    out_features: usize,
    outputs: &mut [f32],
) -> Result<(), String> {
    if batch == 0
        || in_features == 0
        || out_features == 0
        || inputs.len() != batch.checked_mul(in_features).ok_or("shape overflow")?
        || weights.len()
            != out_features
                .checked_mul(in_features)
                .ok_or("shape overflow")?
        || bias.len() != out_features
        || outputs.len() != batch.checked_mul(out_features).ok_or("shape overflow")?
    {
        return Err("dense shapes must be inputs=[batch,in_features], weights=[out_features,in_features], bias=[out_features], outputs=[batch,out_features]".into());
    }
    for b in 0..batch {
        for o in 0..out_features {
            let mut sum = bias[o];
            for i in 0..in_features {
                sum += inputs[b * in_features + i] * weights[o * in_features + i];
            }
            outputs[b * out_features + o] = sum;
        }
    }
    Ok(())
}

Use an optimized build. Debug Rust adds checks and omits the optimizations that production numerical code normally receives. Run from the course root:

cargo test --manifest-path projects/ch25/Cargo.toml
cargo run --release --manifest-path projects/ch25/Cargo.toml
cargo run --release --manifest-path projects/ch25/Cargo.toml -- --large

The no-argument run is deliberately small: batch=32, in_features=64, out_features=32, with three warmups and eleven measured repetitions. --large selects 256, 512, and 256 respectively, with twenty-one repetitions. It is opt-in because useful teaching should not make a long computation the price of checking installation.

Instant supplies elapsed wall-clock time. It is monotonic on supported platforms, but operating-system scheduling, frequency changes, interrupts, and competing work still create variation. Warmups reduce one-time effects such as cold instruction paths. Repetitions expose variation. Sorting durations and selecting the middle sample gives the median: for 9, 10, 11, 15, and 40 microseconds, the median is 11 microseconds. The isolated 40 does not dominate it, and the range 9…40 microseconds remains visible rather than being discarded. The reference stores samples as Duration, whose debug display includes the appropriate unit such as ns or µs; the starter’s median_ns and Rustlings exercise use u128 values that are explicitly nanoseconds.

black_box makes it harder for the compiler to prove that inputs or outputs do not matter and delete the work. It is a best-effort optimization barrier, not a security primitive and not a substitute for inspecting generated code. The output checksum is also consumed and printed. Neither device validates correctness, which is why the reference comparison runs independently.

Never time a single debug run.

A single result cannot show variability, and a debug build measures different code. Record the CPU, compiler version, operating state, dimensions, precision, flags, warmups, repetition count, statistic, and whether allocation or I/O is inside the interval.

3. Turn elapsed time into comparable work

Latency answers how long this run took. Throughput divides useful work by time. A dense pass computes batch×out_features dot products, each with in_features multiply-add pairs. Its conventional operation count is 2×batch×in_features×out_features FLOPs. For inputs [32,64] and weights [32,64], the count is 2×32×64×32=131,072 FLOPs.

If the measured median were 50 microseconds, the reported rate would be 131,072/(50×10−6)/109=2.621 GFLOP/s. That number is illustrative. The executable prints what it measures on your machine. Do not copy the example into a performance claim.

Throughput helps compare sizes whose work counts differ, but it does not make every benchmark comparable. Small inputs may live in cache and spend a large fraction of time in loop overhead. Large inputs may reach memory limits. Different formulas can count operations differently. Keep latency with its unit, dimensions, precision, and counting convention beside the rate.

A profiler answers where time or hardware events occur. On Linux, perf stat can count cycles, instructions, and cache events when system permissions allow it:

perf stat -r 5 cargo run --release --manifest-path projects/ch25/Cargo.toml -- --large

This measures the whole process, including startup and allocation, so it complements rather than replaces the internal kernel timer. A sampling profile can locate hot functions. Start with elapsed time and a profile; optimize only a hotspot large enough to affect the real training or inference workload.

4. Ask whether arithmetic or data movement sets the pace

Processors compute only on data they can reach. Values travel through a memory hierarchy: registers, several cache levels, and main memory. Reusing a weight while it is nearby can be much cheaper than fetching it repeatedly from farther away. A kernel may wait for data even though its arithmetic units could perform more operations.

Arithmetic intensity is useful FLOPs divided by bytes transferred at a stated memory boundary. The boundary matters. Bytes between DRAM and the last-level cache differ from bytes between a core and L1. The project prints a cold-array traffic estimate: read inputs, weights, and bias once, and write outputs once. Under that first-access assumption, additional traffic can come from cache capacity, write allocation, and repeated loads. Warmed repeated calls may already find these arrays in cache, so this estimate is not a lower bound on measured DRAM traffic for the timed calls.

An intensity estimate under a cold-array assumption

Take batch=2, in_features=3, and out_features=2. Inputs contain 6 values, weights contain 6, bias contains 2, and outputs contain 4. At four bytes per f32, the read-once/write-once traffic estimate is (6+6+2+4)×4=72 bytes. Work is 2×2×3×2=24 FLOPs. The estimate is 24/72=0.333 FLOP/byte. If every weight is fetched twice rather than reused, actual traffic rises and actual intensity falls.

The Roofline model compares arithmetic intensity with two machine ceilings: peak arithmetic throughput and memory bandwidth. At low intensity, attainable FLOP/s is limited roughly by bandwidth×intensity. At high intensity, compute capacity becomes the ceiling. This is a diagnostic model, not a promise that code reaches either roof. Instruction mix, vectorization, dependencies, cache conflicts, and threading also matter.

The lesson’s read-once/write-once calculation is deliberately labeled an estimate. To claim DRAM intensity, measure traffic at that level with suitable counters or tools. Still, the calculation guides the next chapter: matrix multiplication performs much more reuse than a vector copy, but a poor loop order can throw that reuse away.

Worked checkpoint

Debugging: the optimized kernel is “100× faster”

A learner allocates and fills vectors inside the baseline timer but prepares them outside the optimized timer. Explain the result.

Answer

The two intervals contain different work, so the ratio does not isolate the kernel change. Decide whether the question is kernel latency or end-to-end latency and place identical boundaries around both versions. Keep allocation outside a kernel benchmark; measure allocation separately if request latency needs it.

Independent variation: batch size and reuse

Measure batch sizes 1, 8, 32, and 128 with fixed in_features and out_features. Record median latency with its unit, GFLOP/s, and the compulsory intensity estimate. Predict which quantity changes linearly before running.

Worked answer

Algorithmic FLOPs grow linearly with batch. Inputs and outputs traffic also grows, while weights and bias can be reused across rows, so the intensity under this traffic assumption rises toward a limit. Measured latency need not scale perfectly: cache state, overhead, and vectorization change the rate. Report the observed curve rather than selecting only the best batch.

6. Review and transfer

Retrieve from memory: Why can two legal f32 reduction orders differ? What work belongs inside this kernel timer? Why report a range beside the median? What does GFLOP/s divide? Why must arithmetic intensity name a memory boundary?

Answers

Floating-point operations round, so reassociation can change low bits. Only the already-allocated dense call belongs inside this timer. The range exposes run-to-run variability hidden by one statistic. GFLOP/s divides the stated useful floating-point operation count by elapsed seconds and one billion. Intensity depends on bytes transferred across a particular level; a compulsory byte estimate is not a measured DRAM count.

A benchmark is evidence about one implementation, shape, build, and machine. It does not establish general speed, hardware saturation, or model quality. In Chapter 26, you keep these measurement rules and change the dense operation’s core matrix traversal to reuse cache lines more effectively.
