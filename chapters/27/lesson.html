A faster scalar matrix kernel still uses one core. Training batches and inference batches contain independent rows, so several cores can evaluate them at once. The difficult part is not creating threads; it is giving each thread unambiguous ownership, preserving the gradient convention, and reducing floating-point results in an order you can explain and test.

Milestone

You will run actual multithreaded inference and training for a linear model. Scoped workers borrow the model and batch, prediction workers own disjoint output slices, training workers produce private loss and parameter-gradient sums, and the parent reduces those shards in fixed index order before one simultaneous update.

1. Partition work along independent examples

The model predicts one scalar from each feature row: ŷr=b+Σfwfinputsr,f. Here r indexes batch rows and f indexes features. Every row reads the same weights and bias, but one row’s prediction does not depend on another. This makes the batch axis a natural partition boundary.

For 10 rows and 3 worker threads, the project computes a ceiling chunk size of ceil(10/3)=4. Worker zero receives rows 0..4, worker one 4..8, and worker two 8..10. The final shard is shorter. Every row belongs to exactly one half-open range, and the ranges remain in ascending order.

Prediction workers share immutable inputs and Model references. The prediction vector is mutable, so it is divided with split_at_mut. Rust proves that the returned slices do not overlap. Each worker writes only its slice, eliminating both a data race and the need for a lock. When all scoped workers finish, the complete batch output remains in original row order. This is the exact partitioning core inside predict_batch_parallel:

thread::scope(|scope| {
    let mut remaining_predictions = &mut predictions[..];
    for shard in 0..shards {
        let start = shard * rows_per_shard;
        if start >= batch {
            break;
        }
        let end = start.saturating_add(rows_per_shard).min(batch);
        let shard_len = end - start;
        let (shard_predictions, rest) = remaining_predictions.split_at_mut(shard_len);
        remaining_predictions = rest;
        let shard_inputs = &inputs[start * in_features..end * in_features];
        scope.spawn(move || {
            for (features, prediction) in shard_inputs
                .chunks_exact(in_features)
                .zip(shard_predictions)
            {
                *prediction = self.predict(features);
            }
        });
    }
});

A scoped thread may borrow stack data because thread::scope guarantees that every spawned thread is joined before the scope returns. Ordinary thread::spawn generally requires owned or 'static data. Scopes let this project borrow slices directly without cloning the model or wrapping everything in reference-counting machinery.

Creating a thread has overhead. A batch of two tiny rows will usually lose to scalar execution. This project teaches ownership and correctness on small data; apply Chapter 25’s release benchmark to find a useful minimum shard size before using the pattern in a latency-sensitive service.

2. Training needs private gradients, then one reduction

For mean squared error L=(1/N)Σr(ŷr−yr)², yr is targets[r], xr,f is the value at row r and feature f in inputs, and er=ŷr−yr. The gradients are:

∂L/∂wf=(2/N)Σrerxr,f;   ∂L/∂b=(2/N)Σrer

The sums make concurrent writes tempting: let every worker add directly into one gradient vector. That would require synchronization on every update and make the addition order depend on scheduling. Instead, each worker owns a zeroed gradient shard. loss_and_gradient_sum loops through its examples in ascending row order and returns (loss_sum, Gradient). The _sum suffix is deliberate: no worker divides by its own shard length, which would give short final shards the same weight as full shards.

for (features, &target) in inputs.chunks_exact(in_features).zip(targets) {
    let error = model.predict(features) as f64 - target as f64;
    loss_sum += error * error;
    gradient_sum.bias += 2.0 * error;
    for (weight_gradient, &feature) in gradient_sum.weights.iter_mut().zip(features) {
        *weight_gradient += 2.0 * error * feature as f64;
    }
}

The parent joins handles in shard order and adds shard zero, then one, then two. Only after all sums are combined does mean_loss_and_gradient divide the loss sum and every parameter-gradient sum by the complete batch size N. Thus loss_and_gradient and loss_and_gradient_parallel both return the same pair: mean MSE and a Gradient of that mean. Finally train_step updates every parameter simultaneously from the completed gradient. Workers never mutate the model they are differentiating.

Reduce two training rows by hand

Use weights=[0.5,−1], bias=0.25. Row zero has features=[1,2] and target=−1: prediction −1.25 and error −0.25. Row one has features=[3,1] and target=1: prediction 0.75 and error −0.25. MSE is ((−0.25)²+(−0.25)²)/2=0.0625.

Worker zero contributes loss sum 0.0625, Gradient.weights sum [−0.5,−1], and Gradient.bias sum −0.5. Worker one contributes 0.0625, [−1.5,−0.5], and −0.5. Summing first and dividing by N=2 gives loss 0.0625, weight gradients [−1,−0.75], and bias gradient −0.5. At learning_rate=0.1, the new model has weights=[0.6,−0.925] and bias=0.3.

The reference stores model and inference values as f32 and accumulates shard losses and gradients in f64. Wider accumulation reduces error; it does not make different groupings exactly equal. The test compares parallel gradients with a scalar whole-batch calculation using absolute and relative tolerances.

3. Define exactly what reproducible means

Deterministic reduction fixes how partial results combine. If workers instead push results whenever they finish, operating-system scheduling can change the order from run to run. Since floating-point addition is not associative, the model may take slightly different updates and diverge over many steps.

This project fixes row ranges, local row order, handle order, and parent reduction order for a chosen thread count. Scheduling changes when a worker finishes, but not where its result appears. On the same build and target, that removes one common source of run-to-run variation.

The promise has boundaries. Changing the thread count can change shard boundaries and therefore grouping. A compiler may introduce fused operations or vector reduction. Different CPUs and compiler flags can produce nearby values. NaNs have additional representation freedom. Record the thread count, toolchain, target features, data order, and seed. Require tolerance-based scalar agreement unless bitwise reproducibility is a tested product constraint.

There are stronger reproducible-summation algorithms, including binned or error-free methods, but they add work and code. They belong when an application truly needs thread-count-independent sums. A fixed reduction order is the smallest useful method for this chapter’s training system.

Deterministic does not mean correct.

A consistently wrong gradient is still reproducible. Preserve a scalar implementation, check a hand-worked example, compare outputs and gradients, and prove that a training step lowers the chosen loss.

Read the complete project. Its deterministic fixture has inputs=[64,4] generated from integer arithmetic and targets=[64] from a known linear rule. The model begins at zero, calls loss_and_gradient_parallel for an initial MSE, trains forty full-batch steps, evaluates again, and calls predict_batch_parallel on eight rows.

The output should show a large decrease in MSE and parameters approaching weights [0.3,0.6,0.9,1.2] with bias 0.25. Exact displayed low digits can vary by environment. This synthetic fit verifies the parallel learning mechanism; it is not a held-out generalization study.

The prediction test compares every output from predict_batch and predict_batch_parallel exactly because each row’s scalar dot product retains the same within-row order. The gradient test compares loss_and_gradient_parallel with scalar loss_and_gradient using tolerance because the cross-row grouping differs. A second test trains with three shards on 31 rows—ranges of 11, 11, and 9—and requires loss to fall by three orders of magnitude. Since all three workers return sums and the parent divides by 31 once, the shorter shard receives exactly its nine-example contribution.

An empty prediction batch returns an empty vector: there is no work and no average. Empty training is rejected because mean loss and gradients would divide by zero. Zero threads, mismatched shapes, and nonfinite training data are also rejected at their boundaries.

For a multilayer network, use the same plan at a larger granularity. Give each worker a batch shard, run complete forward and backward passes with shared read-only parameters, return one private gradient for every parameter, reduce in fixed order, average once, and apply one optimizer update. Do not update shared weights while another worker still computes a gradient from the old model.

5. Practice ownership and reduction

Guided exercise: reduce private gradients

Open ch27_01.rs. reduce_gradient_sums_in_order receives the Gradient.weights vectors returned by real workers and combines them in shard order. It deliberately returns a sum; in the project, mean_loss_and_gradient divides this complete result by the full batch size afterward.

Hint 1

Create a zero vector with the width of the first worker’s Gradient.weights, or zero width when there are no shards.

Hint 2

Loop through worker vectors in their existing order, then zip the total with the current shard and add. Do not divide inside this primitive.

Solution
fn reduce_gradient_sums_in_order(shard_weight_gradients: &[Vec<f64>]) -> Vec<f64> {
    let mut total = vec![0.0; shard_weight_gradients.first().map_or(0, Vec::len)];
    for shard in shard_weight_gradients {
        for (sum, value) in total.iter_mut().zip(shard) {
            *sum += value;
        }
    }
    total
}

The project already validates parameter width before creating workers. The tiny exercise fixes equal vector lengths so the ordered reduction stays visible.

Project checkpoint: parallelize a scalar loss

Run cargo run --manifest-path projects/ch27/starter/Cargo.toml. Its Model has the same fields and predict(&self, features) implementation as the reference, with bias initialized to zero for this fixture. model.loss(inputs, targets, in_features) reports mean squared error. Its test reaches a TODO in model.loss_parallel(inputs, targets, in_features, threads). That method is the loss-only predecessor of the reference’s loss_and_gradient_parallel: partition rows, spawn scoped workers that return loss sums, and reduce handles in creation order before dividing once by the full batch size.

Progressive hint

Choose shards=min(threads,batch), compute a ceiling rows-per-shard, and spawn only nonempty ranges. Capture immutable slices. Collect join handles in a vector. Calling join through that vector preserves shard order even when completion order differs.

Reference checkpoint

Compare with the reference, where each worker extends the same result from one loss_sum to (loss_sum, Gradient). Reduce every sum, call mean_loss_and_gradient once, and update the model only after the scope and reduction complete.

Debugging: results vary between runs

Workers lock one global gradient and add whenever scheduled. All accesses are race-free, yet low bits change.

Answer

A mutex prevents simultaneous memory access but does not fix acquisition order. Different addition orders round differently. Give workers private gradients, store them by shard index, and reduce in a fixed order after joining.

Independent variation: choose a shard threshold

Add a rule that uses scalar inference below a chosen number of rows. Benchmark 1, 8, 64, and 1024 rows with one and four workers.

Worked answer

The correct threshold is measured, not derived from core count alone. Thread creation and joining can dominate small work; larger rows can amortize it. Record feature width too, because one row with 4096 features contains more work than one with four. Preserve the same scalar outputs on both sides of the threshold.

6. Review and transfer

Retrieve: Why partition batch rows? How do predict and predict_batch_parallel differ? How does split_at_mut remove an output lock? What must a training worker return? Where is the batch average applied? Why does join order matter? What changes when the thread count changes?

Answers

Rows are independent under fixed parameters. predict returns one task prediction, while predict_batch_parallel is its threaded batch wrapper. Disjoint mutable slices give exclusive ownership at compile time. A worker returns (loss_sum, Gradient), with summed weight and bias derivatives. mean_loss_and_gradient divides complete totals by N once. Fixed join/reduction order prevents scheduling from changing grouping. A different thread count changes shard boundaries and may change floating-point low bits.

The implementation uses operating-system threads per call and does not claim speedup for tiny work. A long-lived pool would reduce launch overhead when profiling shows repeated calls justify it. In Chapter 28, each core processes several f32 lanes per instruction while retaining scalar fallbacks and correctness checks.

The starter’s reduction test includes a nonzero residual, so an implementation that simply returns zero cannot pass. The reference also checks a two-row gradient against hand arithmetic and rejects non-finite data, parameters, predictions, and gradients. Before updating, it verifies that the proposed parameters remain representable, leaving the existing model unchanged if that step would overflow.
