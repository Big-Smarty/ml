Why does a tensor with the right number of values still fail?

A scratch layer stores weights as two output rows with three inputs each:

[0.2−0.40.60.70.1−0.2],

with biases [0.05,−0.2]. At input [1.5,−2,0.5], its two outputs are [1.45,0.55]. A runtime that expects three input rows with two outputs each cannot obtain the same function by merely reshaping those six values.

The first output is 0.2×1.5+(−0.4)×(−2)+0.6×0.5+0.05=1.45. The second is 0.7×1.5+0.1×(−2)+(−0.2)×0.5−0.2=0.55. Every coordinate carries meaning: weight [output,input] multiplies that input and contributes to that output.

The runtime expects

[0.20.7−0.40.10.6−0.2],

shape [3,2]. This is a transpose of the coordinate map. Reshaping the flattened values instead gives [0.2−0.40.60.70.1−0.2], a different function. Non-square shapes and distinct values make the error conspicuous; a symmetric 2×2 fixture can hide it.

Can two wrong outputs cancel in a passing check?

Expected outputs [1,2] and actual outputs [2,1] both sum to 3. A check of summed output or summed signed error passes despite two wrong coordinates. Compare each corresponding coordinate with

|a−b|≤atol+rtol×max⁡(|a|,|b|),

after checking equal length and finiteness.

The shared tolerance is atol=10−10 and rtol=10−8 for these f64 operations. Absolute tolerance protects near-zero comparisons; relative tolerance scales with magnitude. Reject nonfinite values explicitly: infinity minus infinity is NaN, and a permissive aggregate can hide where it entered.

Use several probes. The worked input mixes signs; [−1,3,0.25] exercises a different balance; zero input isolates biases. A single input leaves many possible weight errors unobserved because different matrices can agree on one vector. Basis inputs would isolate individual columns even more directly.

Keep scratch and runtime forward loops independently organized. Scratch computes one output-row dot product at a time; runtime starts from biases and accumulates input rows into every output. Calling the scratch forward from both sides would verify only the test harness, not an independent convention.

Which loss convention determines the gradient?

The fixture uses half the sum of two squared output errors:

L=0.5∑o(y^o−yo)2.

For target [1,−0.5], errors are [0.45,1.05]. The output gradient equals that error vector. Averaging over the two outputs would divide it by two; using a full sum of squares would multiply it by two.

The scratch gradient has shape [2,3]. Its first row is 0.45×[1.5,−2,0.5]=[0.675,−0.9,0.225]; second row is [1.575,−2.1,0.525]. Bias gradient is [0.45,1.05]. Runtime gradients instead occupy [3,2], with each input row containing that input times both output errors.

What does a file prove about another runtime?

The default interchange format is deliberately fixed: the eight-byte header S09AFF01, then six row-major scratch weights and two biases as little-endian f64 values. Total size is 8+8×8=72 bytes. It is a custom affine fixture, not ONNX and not a general graph format.

Export writes a new file and refuses to overwrite an existing path. Import reads at most 73 bytes so it can reject extra payload beyond the exact format. The parser rejects a wrong header, wrong length, truncated values, and nonfinite parameters before constructing the model.

Use just lab 55 export /tmp/s09-affine.bin, then just lab 55 import /tmp/s09-affine.bin. These commands exercise actual filesystem interchange between invocations. A successful decode still needs the runtime comparisons you implemented.

General model interchange would also need named operators, shapes, dtypes, graph connectivity, supported-op versions, and runtime semantics. Serializing six weights demonstrates the boundary mechanics, not portability of an arbitrary transformer.
