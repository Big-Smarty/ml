1. Which time are you trying to improve?

Chapter 31 kept training state on the GPU. Performance work begins by naming an interval. A CPU timer around command submission measures something different from a device counter around a compute pass. Confusing them can turn a correct number into a false conclusion.

The project applies affine transform q = 1.5x + 0.25 followed by ReLU y = max(q,0) to 65,537 deterministic values. One path uses separate shaders and a storage intermediate. One fuses both expressions. An optional path uses f16 arithmetic when the adapter supports it and the inputs are in a safe range.

separate: input → affine → intermediate → ReLU → output
fused: input → affine + ReLU → output
fn affine_relu_scalar(input: &[f32]) -> Vec<f32> {
    input
        .iter()
        .map(|value| (value * 1.5 + 0.25).max(0.0))
        .collect()
}

We warm up three times, collect seven samples, check every measured output against the scalar oracle, and only then report medians and ranges. Those measured values describe the named adapter, driver, workload, and boundaries. They are not universal speed claims.

2. Keep host latency and device duration separate

CPU wall-clock latency begins after initial buffer and query allocation, before bind-group creation and command encoding, and ends after output mapping. It includes host encoding, submission, scheduling, GPU work, output copy, polling, and output map completion. It answers: how long did this callable GPU path delay the CPU?

A GPU timestamp is a device counter written at each compute pass boundary. Rust resolves the 64-bit ticks into a QUERY_RESOLVE buffer, copies them to MAP_READ staging, then multiplies differences by queue.get_timestamp_period(). For separate kernels, the project sums the two pass intervals. That device-time sum excludes CPU work and may exclude time between passes. The CPU wall clock stops before the host maps and decodes the timestamp staging buffer.

Read the units

If a timestamp difference is 3,560 ticks and the period is 1 ns per tick, device duration is 3,560 ns = 3.56 μs. A wall measurement of 218 μs is not contradictory: it encloses much more work. Subtracting these values as though they shared a boundary would be meaningless.

Timestamp queries are optional. The adapter is queried before device creation; TIMESTAMP_QUERY is requested only when present. Otherwise output remains correct and the report says device timestamps unavailable.

3. Design a measurement that can be repeated

Compilation, initial allocation, and first-use driver work can dominate a tiny kernel. The reference creates pipelines once, then performs three unreported warmups for each plan. It collects seven reported samples while alternating separate, fused, and mixed paths. Alternation reduces the chance that a slow background interval affects only one plan. Seven observations remain a small experiment, so the program reports the middle value and full observed range.

The deterministic input length 65,537 is one beyond 65,536. It forces a partial final workgroup and prevents an exact power-of-two shape from hiding bounds bugs. Every measured output is checked against the scalar expression. A correctness failure aborts the run before any timing summary is printed.

For a stronger study, lock power settings where appropriate, record temperature and clocks, run more samples, and separate allocation, upload, kernel, and readback phases. Those additions answer new questions. They are omitted from the default because this chapter's goal is to distinguish clocks and test fusion, not build a general benchmark harness.

Compare distributions, not decorative precision.

A duration printed to six decimal places is not known to six decimal places. Scheduler noise, frequency changes, and background work remain. Median resists one unusually slow sample; the range shows observed variability. If two ranges overlap heavily, gather more evidence before declaring one design faster. Always preserve the raw unit and workload description so another person can repeat the comparison. Record whether validation and readback were included as well.

4. Submission is asynchronous until you require an answer

queue.submit enqueues a finished command buffer and returns control. The CPU can prepare later work while the GPU executes. Synchronization happens when this program requests staging-buffer mapping and calls device.poll(PollType::wait_indefinitely()). The mapping callback and standard-library channel make completion explicit.

self.queue.submit([encoder.finish()]);
let output = read_f32(&self.device, &readback, input.len())?;
let cpu_wall_time = cpu_wall_started.elapsed();

Asynchrony helps only when independent work exists. Immediately waiting after every tiny kernel serializes host and device and magnifies fixed overhead. Chapter 31 encoded hundreds of ordered passes before one submit. This benchmark must read output for correctness, so each timed sample eventually waits. A serving pipeline might instead keep several requests in flight and collect callbacks later.

Move the timer deliberately.

Starting after submit measures waiting, not submission. Starting before data generation measures preprocessing too. Neither is inherently wrong, but the label must state the boundary. This project allocates bulk buffers before the wall timer and includes bind groups, encoding, submit, copy, and readback.

5. Remove an intermediate with fusion

For N elements, separate affine and ReLU kernels perform N input reads, N intermediate writes, N intermediate reads, and N output writes: 4N storage-value accesses. Kernel fusion performs N reads and N writes: 2N storage-value accesses. It also removes one dispatch. This count describes the operation graph; affine_relu_scalar and affine_relu_with_gpu describe the values computed.

Storage accesses for 1,024 elements

storage_value_access_count returns 4,096 for separate kernels and 2,048 for fused. At four bytes per f32 value, the model corresponds to 16 KiB versus 8 KiB. These are algorithmic storage-access counts, not measured bus bytes: caches, memory transactions, and compiler transformations affect physical traffic.

@compute @workgroup_size(64)
fn fused(@builtin(global_invocation_id) id: vec3<u32>) {
    if (id.x < dispatch_params.element_count) { output[id.x] = max(input[id.x] * 1.5 + 0.25, 0.0); }
}

Fusion is not automatically faster. A large fused kernel may use more registers, constrain schedules, or duplicate work. This tiny chain is a clean case because the intermediate has one consumer. Every plan is checked against the CPU oracle before its timing is compared with the other plans.

6. Select mixed precision by feature and range

Mixed precision changes numeric behavior. The optional shader reads f32, converts to f16, performs affine and ReLU in f16, then writes f32. It begins with enable f16;. Rust creates this shader only when Features::SHADER_F16 is reported and requested.

let available = adapter.features();
let timestamp_queries = available.contains(wgpu::Features::TIMESTAMP_QUERY);
let shader_f16 = available.contains(wgpu::Features::SHADER_F16);
eprintln!(
    "selected hardware adapter: {} ({:?})",
    info.name, info.backend
);
eprintln!(
    "optional features: timestamp_query={timestamp_queries}, shader_f16={shader_f16}"
);
let mut required_features = wgpu::Features::empty();
if timestamp_queries {
    required_features |= wgpu::Features::TIMESTAMP_QUERY;
}
if shader_f16 {
    required_features |= wgpu::Features::SHADER_F16;
}

The same boolean gates f16 pipeline creation. Selection then requires the mixed plan, that pipeline, and a safe input range:

let use_f16 = matches!(plan, Plan::Mixed)
    && self.fused_f16.is_some()
    && f16_arithmetic_is_safe(input);

Finite f32 values may exceed f16's finite range. The teaching path selects f16 only when every |x| ≤ 40,000, which keeps 1.5x + 0.25 inside the approximate half range. Otherwise it uses f32. For this small bounded fixture, output tolerance expands from 1e−5 to 0.01 because fewer f16 significand bits round intermediate values. The range guard prevents overflow; it does not guarantee 0.01 accuracy for every input within that range.

At Vulkan's lower layer, a Vulkan extension separates concerns. VK_KHR_shader_float16_int8 exposes 16-bit arithmetic. VK_KHR_16bit_storage controls 16-bit storage and interfaces. VK_KHR_cooperative_matrix exposes supported subgroup matrix operations. wgpu's portable feature query handles ordinary f16 arithmetic; it does not promise every cooperative matrix shape.

Concrete extension exercise

Suppose a device reports 16-bit storage but not shaderFloat16 arithmetic. May this WGSL kernel perform f16 multiplication?

Answer

No. Storage capability and arithmetic capability are distinct. The program must keep arithmetic in f32 or reject that path. Conversely, arithmetic support does not imply every storage location accepts 16-bit values.
