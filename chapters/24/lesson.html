Classification chooses among fixed labels. Recommendation chooses an ordered list whose candidates and relevance differ by user. A compact recommender can learn one vector per user and item, train those vectors to rank observed preferences above negatives, and evaluate whether held-out relevant items appear near the top.

Your milestone

You will train two-factor user and item embeddings with a stable pairwise logistic loss. One positive item per user remains outside optimization. You will rank that item against three explicit negatives and compute Recall@2, Precision@2, and nDCG@2 by hand and in Rust.

Code and terminology carried forward

Chapter 23 learned parameters by repeating optimizer updates for a chosen number of epochs, kept evaluation targets outside training, and distinguished the model's numerical prediction from mean squared error. Chapter 24 keeps those boundaries and the name learning_rate. The justified change is the task: a recommender produces a raw user-item score for ordering candidates, trains that score with a regularized pairwise loss, and evaluates the resulting lists with ranking metrics. A score is not a probability, and Recall@k is not the training objective. See the course code and terminology guide.

The learned state is now two lookup tables. users: [[f64; FACTORS]; USERS] has logical shape [users, dimension], and items: [[f64; FACTORS]; ITEMS] has shape [items, dimension]. Here those shapes are [4,2] and [6,2]. A user or item ID selects a row; the ID itself is not multiplied as a numeric feature.

A TrainingTriple is (user, positive, negative): all three entries are IDs. Compared with the earlier (input, target) dataset, the desired answer is now an ordering between two items for a user. The extra regularization argument controls the stated L2 term. loss(data, regularization) uses exactly the supplied triples, including for held-out loss evaluation; the separate ranking demonstration uses its declared fixed candidate sets. The small private implementation asserts nonempty data, valid IDs, and distinct positive/negative items.

1. Turn identifiers into learned coordinates

An embedding is a vector representation of an entity or input. It can be obtained from a lookup table or computed from an input by an encoder. This chapter uses the learned-lookup case: a user ID such as 3 has no useful numeric distance from user ID 2, so the ID only selects a table row. Each row contains learned coordinates.

User u's score for item i is s(u,i) = Σf=1..2pu,fqi,f, the dot product of user vector p and item vector q. A larger value means a stronger modeled preference. Scores need not be probabilities and have no calibrated universal scale.

fn score(&self, user: usize, item: usize) -> f64 {
    self.users[user]
        .iter()
        .zip(self.items[item])
        .map(|(a, b)| a * b)
        .sum()
}

The standalone exercise calls this arithmetic dot(user_embedding, item_embedding). The model method score(user, item) first looks up those two rows and then performs the same coordinate-pair multiplication and sum. Its two usize arguments are IDs; the primitive's two slice arguments are already-resolved embeddings.

Score two items

Let a user vector be [1,2]. Item A is [0.5,0.2], giving score 1×0.5 + 2×0.2 = 0.9. Item B is [−0.1,0.4], giving −0.1 + 0.8 = 0.7. The model ranks A first. Rotating every user and item vector by the same angle would change the coordinates but preserve dot products, so factor one should not automatically be named “action preference.”

Collecting user embeddings as rows of P and item embeddings as rows of Q produces the score matrix PQT. This is matrix factorization: a large sparse user-item relationship is approximated through a low-dimensional shared space. Two factors force strong sharing; more factors increase capacity and cold data requirements.

The interaction matrix is incomplete. A missing click can mean dislike, lack of exposure, or simply no opportunity. Treating every missing cell as a confident negative invents labels. The course fixture avoids that ambiguity by supplying three explicit negatives for each user. Real implicit-feedback systems need an exposure or sampling policy and often confidence weights.

2. Train an ordering directly

A pairwise ranking example is (u,i,j): user u prefers positive item i to negative item j. Define margin d = s(u,i) − s(u,j). The pairwise data-loss term is softplus(−d) = log(1+exp(−d)). It is large when the negative outranks the positive and approaches zero as the positive margin grows. triple_loss adds its L2 regularization term to this data-loss term.

The implementation computes softplus stably. For positive x, x + log(1+exp(−x)) avoids exp(x) overflow. For nonpositive x, log(1+exp(x)) is already safe. This preserves the exact logistic objective rather than clamping a probability.

Compute one pairwise update signal

If the positive score is 0.9 and negative score is 0.7, d = 0.2 and the data-loss term is log(1+exp(−0.2)) ≈ 0.5981. Let a = sigmoid(−d) ≈ 0.4502. The code names a ordering_signal; it is a derivative factor, not a calibrated probability that the item should be recommended. The data-loss derivative with respect to d is −a. Increasing the positive score lowers loss; increasing the negative score raises it. If d were −2, a would be about 0.881, creating a larger corrective signal.

For user vector p, positive item qi, and negative qj, gradients without regularization are −a(qi−qj), −ap, and +ap. triple_loss adds λ times the sum of squared coordinates across those three selected vectors, so its gradients add 2λ times each vector. All three gradients use copies of the old vectors before simultaneous update. Reusing a modified user vector for the item update subtly changes the algorithm.

The training set has two positives per user, hence eight triples per epoch. Each positive is paired with a declared explicit negative in deterministic order for 800 epochs. model.loss(&TRAIN_DATA, regularization) sums the eight regularized triple_loss values and divides by eight. model.train(&TRAIN_DATA, epochs, learning_rate, regularization) makes one update per supplied triple. Both methods receive their data explicitly; neither reads the fixture internally. This resembles the pairwise objective used by Bayesian Personalized Ranking, but it is a tiny fixed-triple teaching loop rather than a full bootstrap sampler. The central-difference test validates one user-factor derivative.

One additional positive interaction per user is held out completely. That specific (user,item) pair never appears in a positive triple, negative triple, loss, or stopping decision; the same item ID may still appear for another user, which is the collaborative signal. Sampling a user's held-out positive as that user's unobserved negative would train the model against its own evaluation target.

3. Evaluate the list the user will see

The regularized pairwise loss tells us whether selected training triples improved. Recommendation serves an ordered list, so evaluation uses separate ranking metrics rather than treating the loss as a metric. For each user query, the project considers a four-item candidate set: one held-out positive and that user's three explicit negatives. Training positives are removed because recommending an already consumed item would inflate an offline list.

For a query q with nonempty relevant set Rq, Recall@k is |Rq ∩ TopK(q)| / |Rq|. Compute this fraction for each query, then average across queries. Here each user has exactly one relevant held-out item, so query recall is one if that item appears by rank k and zero otherwise. That special case also equals HitRate@k; with several relevant items, hit rate asks only whether at least one appears and is not Recall@k. Precision@k is relevant items in the top k divided by k. At k=2 with one hit, recall is 1 and precision is 1/2.

nDCG rewards earlier ranks. With one binary relevant item, ideal DCG is one. A hit at zero-based rank r contributes 1/log2(r+2). Rank one contributes 1/log2(3) ≈ 0.6309, while rank zero contributes one.

Compare two top-two lists

User A's held-out item appears first, so Recall@2 = 1, Precision@2 = 0.5, and nDCG@2 = 1. User B's held-out item appears second, giving 1, 0.5, and about 0.6309. Averaging the two users gives Recall@2 = 1, Precision@2 = 0.5, and nDCG@2 ≈ 0.8155. Recall and precision tie, but nDCG recognizes the better first position.

The candidate set is part of the metric. Ranking one positive against three explicit negatives is easier than ranking the full catalog or thousands of sampled negatives. The project does not claim full-catalog ranking. Candidate generation, availability, filtering, and exposure should be recorded alongside metrics in a real evaluation.

Offline relevance also reflects historical policy: users can interact only with items they saw. High Recall@k does not prove a recommendation causes satisfaction, and aggregate ranking metrics can hide poor coverage or unequal quality across groups. These concerns need product-specific analysis and, eventually, careful online experiments.

4. Train and inspect the tiny recommender

Read the complete reference implementation. It initializes deterministic small vectors, optimizes stable pairwise loss with λ = 0.002 and learning rate 0.04, then reports the same frozen four candidate items per user before and after training.

cargo test --manifest-path projects/ch24/Cargo.toml
cargo run --release --manifest-path projects/ch24/Cargo.toml

The authoring run measured:

regularized pairwise training loss 0.69065 -> 0.02021
held-out Recall@2 75.0% -> 100.0%, Precision@2 37.5% -> 50.0%, nDCG@2 65.8% -> 100.0%
user 0: held-out item 2, ranked candidates [2, 5, 3, 4]
user 1: held-out item 1, ranked candidates [1, 5, 3, 4]
user 2: held-out item 5, ranked candidates [5, 2, 0, 1]
user 3: held-out item 4, ranked candidates [4, 2, 0, 1]

All four held-out items rank first after training, so at k=2 every query's recall is one, precision is one half, and nDCG is one. Averaging those four query-level values therefore gives 1, 0.5, and 1. On this one-relevant-item fixture Recall@2 also equals HitRate@2. The improvement happens because users 0–1 share positive items from one group while users 2–3 share another, allowing factorization to place related users and items together.

This fixture contains four users, six items, two factors, explicit negatives, and one held-out positive each. It was designed to make the mechanism observable. It says nothing reliable about sparse production catalogs, new users, evolving interests, or exposure bias. The printed lists include only four candidates even though item IDs range from zero through five.

The tests check numerical gradient agreement, stable finite softplus at ±1000, lower training loss, and improved held-out ranking. The last check is deliberately tolerant of rank ties but deterministic tie-breaking uses item ID, so repeated runs remain inspectable.

Debugging · The held-out metric collapses

A learner removes one positive per user for evaluation, then samples all unobserved items as training negatives. The removed item is frequently sampled.

Answer

The optimizer is explicitly pushing the evaluation positive downward. Separate known negatives from unknown items, or define a negative-sampling policy before selecting the held-out target and exclude evaluation positives. Document the assumption; missing interaction is not automatically dislike.

Independent variation · Add user and item biases

Extend the score to μ + bu + bi + pu·qi. Derive the pairwise gradients before coding.

Worked answer

In the difference s(u,i)−s(u,j), global μ and user bias bu cancel. If a = sigmoid(−d), the positive and negative item biases remain with derivatives −a and +a respectively, plus regularization. This is a useful discovery: a parameter can matter for absolute rating prediction yet be unidentifiable from a same-user pairwise loss.

ID magnitude has no semantic distance; it selects a learned row. The score is a raw user-item vector dot product, not a probability. Pairwise loss directly increases positive-over-negative margins. Recall measures the fraction of each query's relevant set retrieved, while nDCG rewards earlier relevant ranks. Difficulty and meaning change with full-catalog, sampled, filtered, or explicit-negative candidates.

The executable omits biases, cold-start features, approximate retrieval, diversity, calibration, fairness, and online evaluation. Those are real system concerns, but the two-factor model is enough to expose embeddings, ranking optimization, and ranking metrics without a library hiding the arithmetic.
