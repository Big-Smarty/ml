A correct training step can become too large for one processor long before its mathematics changes. The central engineering question is therefore precise: where can we divide the work, what must workers communicate, and how can we prove that the divided update still means the same thing?

The checkpoint

You will run real local worker threads. They exchange gradient sums, partial dot products, activations, and activation gradients through Rust channels. The project compares every partitioned calculation with a serial reference and resumes a two-minibatch run from serialized state. It demonstrates communication semantics on a CPU; it does not execute on multiple GPUs.

1. From one training loop to several workers

Recall the full-batch linear regression update from earlier chapters. For example i, let xᵢ be a four-component input, yᵢ its target, w the four weights, and b the bias. The prediction is ŷᵢ = w·xᵢ + b. With mean squared error L = (1/N)Σᵢ(ŷᵢ−yᵢ)², the weight gradient is (2/N)Σᵢ(ŷᵢ−yᵢ)xᵢ and the bias gradient is (2/N)Σᵢ(ŷᵢ−yᵢ). N is the number of examples. The sum is the expensive part; addition lets us divide it.

Data parallelism gives each worker a replica of w and b but a different group of examples. Every worker must read the same parameter snapshot. It computes a local gradient sum and sends the sum plus its example count to a coordinator. The coordinator adds messages in a fixed worker order, divides by the total count, and applies one update. If replicas instead update before exchanging gradients, they no longer implement the same synchronous step.

Uneven workers by hand

Suppose worker 0 sees one example and reports a weight-gradient sum of 4. Worker 1 sees three examples and reports a sum of 6. The full-batch mean is (4 + 6)/(1 + 3) = 2.5. Averaging the two worker means gives (4/1 + 6/3)/2 = 3, which is wrong because the first example receives three times the weight of each example on worker 1. Sending sufficient statistics—the sum and count—keeps the reduction correct for uneven slices.

The project creates two scoped threads, clones a channel sender for each, and sends a typed Gradient containing worker id, four weight sums, bias sum, and count. The receiver sorts by worker id before addition. Sorting is not needed for real-number algebra, but floating-point addition is not associative: (a+b)+c can round differently from a+(b+c). A stable local order makes the check reproducible. Production collectives may use different trees or rings, so mathematical equivalence normally means agreement within a tolerance rather than identical bytes.

2. Partition one tensor operation

Tensor parallelism divides one operation and its parameters. Split our dot product after feature two. Worker 0 owns w₀,w₁ and returns p₀ = w₀x₀ + w₁x₁. Worker 1 owns w₂,w₃ and returns p₁ = w₂x₂ + w₃x₃. The coordinator constructs ŷ = p₀ + p₁ + b. Neither partial is a prediction by itself.

Forward and backward across a shard boundary

Let w = [1, 2, −1, 0.5], x = [2, 1, 3, 4], b = 0, and y = 0. Worker 0 returns 1×2 + 2×1 = 4. Worker 1 returns −1×3 + 0.5×4 = −1. The global prediction is 3, so the derivative of squared error with respect to the prediction is δ = 2(3−0) = 6. The coordinator sends this shared δ to the shards. Worker 0 forms [δx₀,δx₁] = [12,6]; worker 1 forms [18,24]. The bias gradient is δ once, not once per shard. Concatenating the two local weight gradients exactly reconstructs 2(ŷ−y)x.

The reference performs both halves with actual threads and channels. It first communicates each example's partial activation, forms the residual centrally, then asks two shard workers for their accumulated parameter gradients. This is deliberately small enough to inspect. On real transformer layers, column and row partitions are chosen around matrix multiplications so some nonlinear work stays local and the necessary reductions occur at explicit boundaries. Communication placement is part of the algorithm, not a detail added after the model is written.

A common bug adds b to every partial activation. With two shards the assembled prediction then contains 2b. Another computes each shard's residual from its partial output, which loses cross-shard information. Debug the boundary by logging the two partials, their sum before bias, the single residual, and the final concatenated gradient. The serial oracle in the complete reference source makes each comparison direct.

3. Send activations forward and gradients backward

Pipeline parallelism assigns consecutive layers to workers. The project adds a two-stage network. Stage 1 owns two scalar hidden units hⱼ = tanh(w¹ⱼx + b¹ⱼ). Stage 2 owns ŷ = Σⱼw²ⱼhⱼ + b². During the forward pass, stage 1 sends each microbatch id, input, target, and hidden activation to stage 2. Stage 2 computes δ = 2(ŷ−y), accumulates d w²ⱼ = δhⱼ, and sends d hⱼ = δw²ⱼ back.

Stage 1 then applies the tanh derivative: d zⱼ = d hⱼ(1−hⱼ²), d w¹ⱼ = d zⱼx, and d b¹ⱼ = d zⱼ. Both stages accumulate all four examples before the coordinator updates either parameter set. Freezing the old weights matters. If stage 2 changes w² before stage 1 calculates d h, the backward pass mixes two model versions and no longer differentiates the forward computation that produced h.

One activation-gradient message

Take scalar input x=1 and target y=1.5. Use stage-one weights [0.2,−0.3], biases [0.1,0], stage-two weights [0.4,−0.2], and output bias zero, matching the fixture. The first stage produces h≈[0.2913,−0.2913]. Stage two predicts 0.4×0.2913−0.2×(−0.2913)≈0.1748, so δ=2(0.1748−1.5)≈−2.6504. Its backward message is d h≈[−1.0602,0.5301]. Since 1−tanh²(0.3)≈0.9151, stage one obtains d z≈[−0.9702,0.4851]. Here x=1, so these are also the first-stage weight gradients for this single example. They are sums until all four microbatches finish; only then does the update divide by four.

Parity alone cannot prove a shared derivative is correct: two implementations may repeat the same algebraic mistake. The pipeline test therefore also perturbs a first-stage weight by ±10⁻⁵, recomputes the scalar mean squared loss, and compares its central slope with the gradient implied by the communicated update. This reaches through both learned stages and the tanh nonlinearity. The serial-versus-threaded comparison then answers the separate question of whether moving that gradient across channels preserved the calculation.

Microbatches let different stages work on different examples at once. A pipeline begins with downstream stages idle while the first activations arrive and ends with upstream stages idle while gradients drain. These idle intervals are called bubbles. More microbatches can reduce the bubble fraction, while increasing scheduling and communication work. Our unbounded standard-library channels expose ordering and ownership but do not measure accelerator utilization or implement a high-throughput scheduler.

Communication is part of correctness.

A channel that never closes can deadlock a stage waiting for the end of a stream. The sender must be dropped after its final activation so stage 2 can finish, close the backward channel, and let stage 1 finish. Treat termination and error propagation as protocol messages, not cleanup trivia.

4. Recovery means restoring the next update

A parameter file can reproduce inference yet fail to reproduce training. Checkpoint recovery must restore every value that controls what happens next. For this linear SGD example that means the model, completed-step count, and minibatch cursor. Adam would also require its first- and second-moment buffers. Random shuffling would require the generator state or an equivalent deterministic position.

Recovery additionally assumes the surrounding configuration is identical. This checkpoint has no learning-rate field because the same fixed rate is supplied explicitly on both paths. It stores no dataset fingerprint, batch-size setting, or scheduler state. Changing any of those can change the next update despite restoring every stored byte. A production resumption format must bind the checkpoint to the corresponding configuration and data version. For this small deterministic fixture, tests keep those inputs fixed and validate the cursor against the actual data length before indexing.

The project advances through batches of three. Starting at cursor 0, the first update consumes examples 0,1,2 and stores cursor 3. After reload, the next update consumes 3,4,5 and returns the cursor to 0. The test compares this result with two uninterrupted updates. The encoded record begins with CH50v1; the decoder rejects unknown versions, wrong field counts, parse failures, and nonfinite parameters. The step increment uses checked arithmetic, and every update rejects nonfinite output before committing it.

The executable serializes to a string and decodes it within the same process; it does not write a file or relaunch a process. This is recovery from a known checkpoint boundary: imagine a worker process stops, the program relaunches, reads the record, and continues. It does not detect worker failure, elect a coordinator, replicate storage, or recover messages that were in flight. Those require a fault model and distributed protocol. Even a complete checkpoint cannot promise bitwise equality after changing hardware or reduction topology. The defensible claim is narrower: with the same local arithmetic and ordered reductions, the resumed state equals the uninterrupted fixture; across execution systems, compare within a documented numerical tolerance.

5. Run and inspect the communication

From the repository root, run the reference:

cargo run --release --manifest-path projects/ch50/Cargo.toml
cargo test --manifest-path projects/ch50/Cargo.toml

The measured default run reports two worker gradient messages, a tensor-parallel prediction, and a tensor update matching serial within 1e−12. A first linear forward-only pipeline communicates six activations for the six-row fixture. The separate trainable two-stage network communicates four microbatches forward and their gradients backward, updates both stages, and matches its serial update. The run ends with recovery equivalence: true. These are local CPU measurements. No output line claims multi-GPU execution, network bandwidth, or speedup.

Start the guided checkpoint with cargo run --manifest-path projects/ch50/starter/Cargo.toml. It prints the local sums from two slices using the serial gradient code you already know. Then run cargo test --manifest-path projects/ch50/starter/Cargo.toml. The intentional TODO asks you to aggregate sums by total example count. The smaller Rustlings version is ch50_01.rs.

Practice: implement, debug, vary

  1. Complete average_worker_gradients in the starter. Preserve sums until the last division.
  2. Debug this failure: batches of four pass, but batch five differs from serial. Inspect slice lengths and determine whether worker means were averaged equally.
  3. Independent variation: change the reference to three data workers. Test batch sizes one, three, and five, including empty slices, without dividing by worker count.
Hint 1: identify the denominator

The objective averages over examples. Add every count; that total is the denominator for both accumulated gradient sums.

Hint 2: pseudocode
total_dw = sum(part.dw)
total_db = sum(part.db)
total_n  = sum(part.count)
return (total_dw / total_n, total_db / total_n)
Worked solution and debugging answer

For the Rustlings scalar, compute let sum: f64 = parts.iter().map(|(s, _)| s).sum(); and divide it by the summed counts. The five-example failure is the signature of averaging worker means when slice sizes differ. With three workers and one example, two workers may legally contribute zero counts and zero sums; reject only when the total count is zero.
