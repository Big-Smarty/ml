# Chapter 24 consistency review

## Interface mapping

- `MatrixFactorization::score(user, item)` remains the model operation. Its `usize` arguments are user and item IDs; it looks up one row from each embedding table and returns their dot product as a raw preference score, not a probability.
- The starter's `preference(user, item)` became `dot(user_embedding, item_embedding)`, matching the Rustlings exercise and solution. This primitive receives resolved vectors. The lesson maps it directly to the dot-product reduction inside `score(user, item)`.
- `train(&mut self, epochs, rate, regularization)` became `train(&mut self, data, epochs, learning_rate, regularization)`; `loss(data, regularization)` replaces the fixture-capturing `mean_training_loss`. The added first data argument makes training explicit; update count, values, old-vector copies, and optimization behavior remain unchanged on the same fixture.
- The local sigmoid derivative factor became `ordering_signal` rather than `q`, avoiding collision with the mathematical item-vector symbol. It is not presented as a recommendation probability.
- `triple_loss` remains the regularized objective for one `(user, positive, negative)` triple. `ranking_metrics(model, k)` remains a separate evaluation operation and is never optimized.

All changed Rust APIs are chapter-local. The only callers are the reference `main` and tests, the starter `main` and test, and the standalone Rustlings files; there are no path dependencies.

## Shapes, loss, and metric reductions

`MatrixFactorization.users` has actual shape `[[f64; 2]; 4]`, logically `[users, dimension]`. `items` has actual shape `[[f64; 2]; 6]`, logically `[items, dimension]`. `score` reduces the two matching coordinates to one raw scalar.

`triple_loss` is `softplus(-(positive_score - negative_score))` plus `regularization` times the sum of squared coordinates in the selected user, positive-item, and negative-item vectors. `loss(data, regularization)` averages the supplied regularized triple losses: two triples for each of four users. Training performs eight immediate updates per epoch.

For every query with nonempty relevant set `R`, Recall@k is `|R intersect TopK| / |R|`; the reported result averages four query-level values. This fixture has exactly one held-out relevant item per query, so its Recall@k equals HitRate@k. The definition and lesson state that the metrics differ when a query has several relevant items. Precision@k and nDCG@k are also computed per query and averaged over the same four queries.
