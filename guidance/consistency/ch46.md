## Final interface mapping

The reference now uses these exact interfaces:

```rust
fn dpo_pair_loss(policy_logratio: f64, reference_logratio: f64, beta: f64) -> f64;

impl Policy {
    fn loss_and_gradient(
        &self,
        reference: &Self,
        data: &[Preference],
        beta: f64,
    ) -> Result<(f64, Gradient), &'static str>;

    fn loss(
        &self,
        reference: &Self,
        data: &[Preference],
        beta: f64,
    ) -> Result<f64, &'static str>;

    fn step(
        &mut self,
        reference: &Self,
        data: &[Preference],
        beta: f64,
        learning_rate: f64,
    ) -> Result<(), &'static str>;
}

fn train_dpo(
    steps: usize,
    learning_rate: f64,
) -> Result<(Policy, [f64; 2]), &'static str>;

fn exact_reward_training(
    steps: usize,
    learning_rate: f64,
) -> Result<Vec<f64>, &'static str>;
```

`Policy` owns learned logits. `Gradient` is a separate type whose nested-vector field has the same shape and contains derivatives. `loss_and_gradient` is fused because loss and derivatives reuse the same policy/reference log probabilities. Its policy, frozen reference, and preference data are explicit arguments. `train_dpo` and `exact_reward_training` remain fixture-specific demo drivers that visibly own their local constants; they are not a generic trainer abstraction.

The starter, Rustlings exercise, solution, and reference all use `dpo_pair_loss(policy_logratio, reference_logratio, beta)`. The solution and reference use the same overflow-safe softplus expression. Optimizer rates are named `learning_rate` throughout ordinary Rust code.

## Shapes, reductions, and step units

- The DPO fixture has policy/reference logits `[prompts, responses] = [2, 3]` and four supplied `Preference` values. `Gradient.logits` is also `[2, 3]`.
- Each pair forms a policy chosen/rejected log ratio and the corresponding frozen-reference log ratio. The stable pair loss is `softplus(-beta * (policy_logratio - reference_logratio))`.
- `loss_and_gradient` returns the arithmetic mean over `data.len()` preference pairs. Every gradient contribution uses the same division, so the loss and gradient reductions agree. All contributions are evaluated before mutation.
- `Policy::step` is one optimizer update. Chapter 45's `environment_step` advances an environment; Chapter 46's DPO and exact-reward paths perform no environment transitions. `steps` in both Chapter 46 demo drivers counts optimizer updates.
- The exact-reward fixture has one prompt and three candidates. Its objective is `sum_i probability_i * reward_i`, a probability-weighted sum over candidate actions, not an arithmetic mean over the three candidates and not a mean over prompts.
- In the language-model explanation, `T` counts response-token positions and is one for this fixture. `τ` is reserved for temperature; no temperature is implemented here.
