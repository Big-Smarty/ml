Your learning workspace

Keep a history of what you learned.

A Git commit can preserve both working code and the explanation that made it click. Use small checkpoints to remember what changed, when you recorded it, and what evidence convinced you.

Your session loop

Try an idea → run its checks → inspect the changes → write what you learned → commit. Push when you want that history available on GitHub.

Start from a known baseline

Complete the workspace setup, then run these commands from the course folder. First check whether it already belongs to a repository:

git rev-parse --show-toplevel
git status --short

If Git reports an existing repository, check that the printed root is the intended course folder and preserve its history. If the first command says this is not a repository, initialize your downloaded copy:

git init -b main

Set your own commit identity for this repository. Replace both placeholders; use your GitHub-provided noreply address if you prefer to keep your personal address out of commits. This identity labels commits; it does not sign you into GitHub.

git config --local user.name "YOUR NAME"
git config --local user.email "YOUR COMMIT EMAIL"

The supplied .gitignore excludes build targets, downloaded datasets, generated pages, local tool binaries, and common model/checkpoint files. Keep those rules. Add patterns for any new model or data formats you introduce; an ignore rule does not remove a file already tracked. Keep small authored fixtures, source files, and reproducibility notes.

For a newly initialized repository, stage the supplied course sources as a baseline before changing experiments. Inspect the staged list before committing:

git add -- .gitignore .helix README.md CHAPTERS.md course.json sections.json rust-toolchain.toml justfile chapters labs projects site tools guidance
git diff --cached --stat
git status --short
git commit -m "Record the starting course workspace"

For an existing repository, inspect its current changes and latest commit instead; do not create a second baseline blindly. Browser practice records live in browser storage. Git does not capture them or turn a checked box into evidence that your Rust checks passed.

Commit one learning checkpoint

Work in labs/s01-foundations/src/ch01.rs. The complete explained implementation is in labs/s01-foundations/src/solutions/ch01.rs. Keep your source and observations together so you can see what changed.

just lab-check 01
just lab-test 01
git status --short
git diff -- labs/s01-foundations/src/ch01.rs

The learning-goal check tests your implementation; the package test checks the supplied baseline and supporting code. Record their actual results. Create notes/ch01.md in your editor with the date, your explanation, a corrected mistake and a question to revisit. An unfinished experiment is a useful checkpoint if you identify what remains unresolved.

git add -- labs/s01-foundations/src/ch01.rs notes/ch01.md
git diff --cached
git commit

Staging selects the exact snapshot for this commit. Changes made afterward require staging again. In the editor Git opens, write a short subject, a blank line, and useful evidence; save and close the editor to finish:

feat(ch01): implement numerical-gradient training

Learned: weight scales the input; bias shifts the prediction.
Corrected: the held-out input must use the same prediction rule.
Checked: learner goal checks pass on both calibration lines.
Next: derive the loss gradient without the reference.

Use this message only when those statements match your work. Prefixes such as feat(ch01) or docs(ch01) are optional; “Explain the Chapter 1 gradient” is also a useful subject. Commit a coherent checkpoint rather than everything changed during a long session. An unfinished experiment can be committed too, provided the message records its failing check honestly.

Find when and what changed

git log --oneline --decorate -12
git log --date=iso-strict --format='%h %ad %s' -- notes/
git show HEAD -- notes/ch01.md labs/s01-foundations/src/ch01.rs

The first command lists recent checkpoints; the second follows your notes with author dates and timezone offsets; the third shows the latest commit’s patch. Replace HEAD with a displayed commit hash to inspect an older checkpoint. You can compare two saved versions with git diff EARLIER_HASH LATER_HASH -- notes/ch01.md.

Commit timestamps record history metadata, not hours studied or proof of understanding. Author and committer dates can differ. If session duration matters, record it yourself in the note. Optional annotated tags give milestones a memorable name:

git tag -a ch01-complete -m "Predictor checked; gradient review next"
git show ch01-complete

Experiment and recover carefully

After committing your current checkpoint, give an experiment its own branch:

git switch -c experiment/ch01-learning-rate

Commit its results there. Return with git switch main if your starting branch is named main; otherwise use its actual name. A branch keeps an experiment’s history reachable even when its result is unsuccessful.

Staged the wrong file? Unstage it without discarding your edits:

git restore --staged -- labs/s01-foundations/src/ch01.rs
Deliberately discard an uncommitted edit

First inspect git diff -- labs/s01-foundations/src/ch01.rs and save any useful work elsewhere. After unstaging, git restore -- labs/s01-foundations/src/ch01.rs replaces that file’s working contents with the committed version. Those discarded edits are not a saved checkpoint.

To undo a committed change while preserving shared history, first commit or stash current edits so the working tree is clean. Inspect its hash with git show COMMIT_HASH, then use git revert COMMIT_HASH. Revert creates a new inverse commit and may require conflict resolution. This is a useful default for history already pushed to GitHub.

Put your learning history on GitHub

Create a new empty GitHub repository with your chosen visibility. Do not initialize it with a README, license, or gitignore when publishing this existing local history. Use your established HTTPS credential manager, GitHub CLI authentication, or SSH key setup; never put a token in the remote URL.

git remote -v
git branch --show-current

If there is no origin, replace USERNAME and REPOSITORY below with your GitHub owner and repository names. Choose one URL style:

git remote add origin https://github.com/USERNAME/REPOSITORY.git
# Alternative for an existing SSH setup:
# git remote add origin git@github.com:USERNAME/REPOSITORY.git
git push -u origin HEAD

If origin already points to the course’s upstream repository, keep it and add your destination with git remote add learning https://github.com/USERNAME/REPOSITORY.git; then use git push -u learning HEAD. If it already points to your intended destination, skip adding it. Verify the URL before pushing. A rejected push deserves inspection, not a force push.

The first push sets the current branch’s upstream; subsequent commits on that branch can use git push. Tags are separate: publish the milestone explicitly with git push origin tag ch01-complete, substituting learning if needed. Open GitHub’s commit history to read your notes and patches. Local commits preserve checkpoints; pushing transfers those committed snapshots.
